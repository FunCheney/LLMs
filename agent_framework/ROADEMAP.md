# 三个月 Agent 工程师学习计划 v2（2026-10-20 起 · 单项目贯穿版）

> **终局目标（唯一验收标准）**：12 周结束时交付**一个**仓库 `growth-agent` —— 能自主完成「主题 → 深度调研 → SEO 文章 → 多平台文案」的 Agent 服务，且具备**生产级工程质量**。评审不看功能数量，看三大稀缺能力的**可验证证据**。
>
> 适用范围声明：目标是"生产级工程质量"，不是"生产级规模"。日均几十次真实调用 + 完整工程闭环，即可支撑面试；不追求百万用户。

## 一、v1 计划的 5 个结构性问题（为什么必须重构）

| # | 问题 | 后果 | v2 对策 |
|---|---|---|---|
| 1 | 收官项目只有 W11 五天（≈12h） | 不可能达到生产级 | 项目 **W1 立项**，每周合流，累计 11 周 ≈ 130h |
| 2 | 框架仓库 + 业务作品双资产 | 两个半成品，讲不清主线 | **单仓库单产品**，框架作为内部包被产品 dogfood |

| 4 | 多智能体（最稀缺技能）仅 5 天且与场景脱节 | 只能讲概念，没有实战取舍 | W9 直接长在 capstone 的调研链路上，产出单/多 Agent 对比数据 |
| 5 | "生产级"无定义 | 无法验收，容易自我感觉良好 | 见第二节 **DoD 九条硬指标** |

## 二、生产级 DoD（Definition of Done）—— 达不到不算完成

| 维度 | 硬指标 |
|---|---|
| 可用性 | 连续 7 天可用；正常成功率 ≥ 95%；注入工具故障后 ≥ 90% 且不崩、不静默失败 |
| 延迟 | `/v1/chat` 首 token p95 ≤ 1.5s；单次完整调研任务 p95 ≤ 120s；有分段耗时拆解 |
| 成本 | 单次完整任务 ≤ ¥2.0；有 per-task 预算上限 + 超支熔断；有成本归因看板 |
| 质量 | golden set（≥50 条）任务成功率 ≥ 80%；LLM-as-Judge 均分 ≥ 4.0/5 |
| 可靠性 | 模型超时 / 工具 500 / 限流 三类故障注入可自愈；长任务可断点续跑；请求幂等 |
| 安全 | 10 条 prompt injection 用例全拦截；工具调用全审计；高风险动作 HITL 审批门 |
| 工程 | 核心模块单测覆盖 ≥ 70%；CI 跑 lint + test + eval 回归门禁；一键部署；可回滚 |
| 可观测 | 任意一次任务可回放完整 trace（含每次 LLM 调用、工具调用、token 与耗时） |
| 文档 | README + 架构图 + ADR ≥ 5 篇 + runbook + **12 周指标趋势图** |

> 这套指标本身就是面试素材：招聘方最缺的不是"会写 Agent"，是"能证明 Agent 可靠"。

## 三、贯穿式 Capstone 机制（v2 的核心变化）

### 3.1 仓库结构（W1 就定好，之后只填充不重构）

```text
growth-agent/
├── packages/agent_framework/     # 框架：llm / memory / knowledge / skills / planner / resilience / eval
├── apps/growth_agent/            # 产品：调研 → SEO → 社媒 pipeline + MCP 工具
├── evals/                        # golden set + 评测脚本 + 历史快照 + CI 门禁
├── ops/                          # Dockerfile / compose / runbook / 告警规则
└── docs/                         # 架构图 / ADR / llm-api-matrix / 调优清单
```

**关键纪律**：框架层只写"被产品真实调用过"的能力。产品先有需求 → 框架再抽抽象，避免过度设计（这也是面试里"你怎么划分框架与业务边界"的答案）。

### 3.2 每周五「合流仪式」（15 分钟，不可跳过）

1. 本周代码合并进 `main`，确保 capstone 端到端仍可跑
2. 跑一次全量评测，把指标写入 `evals/history/YYYY-Www.json`
3. 更新趋势图（成功率 / p95 / 单任务成本 / judge 分）
4. 记一条 `docs/log.md`：本周做了什么、指标变化、遗留问题

> 12 周 12 个数据点连成曲线，是你区别于"教程克隆"的最强证明。

### 3.3 上线与真实使用（很多候选人缺的就是这一环）

- W10 Day5 部署到真实可访问环境，开始给自己 + 2~3 位朋友真实使用
- W11 用真实反馈修 bug，记录「线上问题 → 根因 → 修复」至少 5 条
- 面试讲"我上线后遇到的最难的三个问题"，比讲架构更有说服力

## 五、12 周计划

> 节奏：每周 5 天 × 2–3h ≈ 10–15h，共约 140h。每周固定四件事：**学概念 → 写代码 → 合流进 capstone → 跑评测**。
> 说明：每周的「产出物」都是 **capstone 的一次增量**，不再有孤立练习。

### Week 1：LLM 适配层 + 首个纵向切片（P0）

> 已展开为可执行清单：架构与契约见 `docs/architecture.md`，逐日任务与验收见 `docs/w1/w1-tasks.md`。

- D1：调研 4 家 API 差异（鉴权/消息结构/tool call 格式/流式协议/usage/错误码）→ `docs/w1/` 下按厂商分文件（Anthropic.md / OpenAi.md / Deepseek.md / Qwen.md），总览与回填表在 `docs/w1/llm-api-matrix.md`；**同一天完成 capstone 立项**（仓库骨架 + README 目标 + DoD 抄进 README）
- D2：内部类型与 `LLMClient` 抽象（chat / stream / capabilities / 统一 `StreamEvent`）
- D3：`openai_compat.py`（覆盖 OpenAI/Qwen/DeepSeek/Ollama）+ `anthropic.py` + `mock.py`
- D4：tool calling 双向归一化；`POST /v1/chat` 支持 stream / 非 stream
- D5：配置化 tier 路由（cheap/strong）+ 统一异常层次 + 结构化日志 + 成本埋点
- **合流点**：capstone 有第一个能跑的 `/v1/chat`（哪怕业务逻辑是空的）
- **检查点**：3 个真实模型 + mock 一键切换；同一组 tool call 断言在 3 个 provider 上参数化 pytest 全绿；`curl -N` 流式可见；错误码规范

### Week 2：运行底座 + 可观测基线 + 评测冒烟集（P0）

- D1：Redis 会话状态；Temporal 承接长任务（流式走直连、分钟级任务走工作流的分层定稿）
- D2：并发控制（Semaphore / 连接池 / 背压）+ 队列异步化
- D3：可观测三件套：结构化日志 + trace_id 贯穿 + token/耗时/成本埋点
- D4：Docker + compose 一键起；locust 压测出基线报告
- D5：**建 10 条 smoke eval**（先能跑，W3 再扩到 50+），接进 CI
- **合流点**：capstone 可一键部署，任意请求可回溯，有第一组延迟/成本基线
- **检查点**：100 并发错误率 < 1%；能从一条请求追到每次 LLM 调用耗时

### Week 3：评测体系 I —— Golden Set 与 Trace（P0，稀缺能力 ①）

- D1：评测方法论：离线/在线、指标分层（成功率/工具错误率/延迟/成本/judge 分）
- D2：为 capstone 构建 50+ 条 golden dataset（含答案、引用、难度分层）
- D3：批量评测脚本 + 结果落盘 + 与 `evals/history` 对接
- D4：接 Langfuse（或 LangSmith），全链路 trace 采集
- D5：评测报告模板 + 失败 case 自动分类
- **合流点**：`make eval` 一条命令出报告
- **检查点**：能回答"当前系统到底多好"，且数字可复现

### Week 4：评测体系 II —— Judge、回归门禁与根因归因（P0，稀缺能力 ①）

- D1：LLM-as-Judge：rubric 设计 + 与人工标注的一致性校验（≥20 条抽样）
- D2：RAGAS：faithfulness / answer relevancy / context precision
- D3：CI 回归门禁（指标劣化即 fail）+ 基线快照
- D4：根因归因方法：从 trace 定位到检索 / 提示词 / 工具 / 模型四层
- D5：写 3 篇「现象 → 根因 → 量化改进」案例
- **合流点**：capstone 有了"改坏了会被拦住"的护栏
- **检查点**：案例含前后指标对比，可 10 分钟讲清

### Week 5：生产 RAG I —— 混合检索与重排（P0）

- D1：BM25 vs 稠密；向量库选型（pgvector / Qdrant）
- D2：混合检索 + RRF 融合，接入 capstone 的「品牌/竞品资料库」
- D3：重排（bge-reranker）+ 延迟预算控制
- D4：Query 改写（multi-query / HyDE）
- D5：用 W3 评测集做 A/B 对比实验
- **合流点**：capstone 能基于自有资料回答问题
- **检查点**：Recall@K / MRR 量化提升 ≥ 10%，有对比报告

### Week 6：生产 RAG II —— 溯源与增量（P1）

- D1：chunk 元数据 + 引用溯源（输出必须带出处）
- D2：增量索引 + 文档版本/删除同步
- D3：ACL-aware 检索最小实现
- D4：lost in the middle 与上下文污染缓解
- D5：RAG 调优清单沉淀
- **合流点**：capstone 报告中的每条结论可溯源
- **检查点**：新增文档免全量重建；引用准确率抽样 ≥ 90%

### Week 7：上下文工程与记忆（P0）

- D1：Context Engineering 全景（每次调用的 payload 设计 + token 预算分配）
- D2：工作记忆：会话状态、对话摘要、tool result 截断
- D3：长期记忆四阶段（提取/写入/检索/遗忘）+ 品牌画像记忆
- D4：长上下文退化（lost in the middle）缓解；记忆与知识库边界
- D5：成本优化实验（压缩前后 token 对比）
- **合流点**：capstone 记得品牌调性、历史选题、禁用词
- **检查点**：20+ 轮不爆上下文；跨会话可回忆；token 成本下降可量化

### Week 8：Skills 系统与 MCP（P0，市场 54% 点名）

- D1：MCP 协议深入（Server/Client、工具发现、协议边界）
- D2：把搜索/抓取封装为 **MCP Server**（capstone 的工具底座）
- D3：Skill 规范设计（元数据 + 指令 + 脚本 + 参数契约 + 沙箱执行）
- D4：Skill 加载器（注册/发现/动态加载）+ 重构 2–3 个工具为 Skill
- D5：工具权限白名单 + 二次确认 + 审计日志
- **合流点**：capstone 具备真实外部检索能力
- **检查点**：新增工具/Skill 不改主流程即可被调用；调用全审计

### Week 9：规划与多智能体（P0，稀缺能力 ③）

- D1：ReAct vs Plan-and-Execute vs Reflection；实现 Plan-and-Execute
- D2：调研规划器（问题拆解 → 子任务 → 执行 → 重规划）
- D3：多智能体：supervisor + researcher + validator 的 handoff 协议、共享状态、**防死循环/预算控制**
- D4：LangGraph 对照实现（同样的图，比较自研 vs 框架的取舍）；了解 A2A 协议
- D5：**单 Agent vs 多 Agent 对比实验**（成功率 / 步数 / 成本 / 延迟）
- **合流点**：capstone 的"深度调研"链路成型
- **检查点**：≥5 步任务完成率显著高于朴素 ReAct；能讲清"何时才值得拆多 Agent"并用数据支撑

### Week 10：内容生成 + 安全护栏 + 首次上线（P0，稀缺能力 ①③）

- D1：SEO pipeline（关键词 → 大纲 → 成文 → meta / 结构化数据）
- D2：多平台风格化改写（小红书 / X / LinkedIn）+ 品牌调性约束
- D3：Prompt Injection 攻防：输入隔离、指令分层、注入检测中间件、10 条红队用例
- D4：Guardrails 分层（输入校验 / 输出过滤 / 行为监控）+ HITL 审批门（发布前人工确认）
- D5：**部署上线**，开始真实使用；写第一版 runbook
- **合流点**：capstone 端到端可用 —— 主题进，调研报告 + SEO 文章 + 3 平台文案出
- **检查点**：注入用例全拦截；端到端跑通且全程有 trace

### Week 11：生产硬化周（P0，稀缺能力 ①）

- D1：SLO 定义 + 告警规则（成功率/延迟/成本三张图）
- D2：容灾强化：混沌演练（模型超时 / 工具 500 / 限流）+ 降级与兜底模型
- D3：幂等与断点续跑；灰度与回滚演练
- D4：用真实反馈修 bug（目标 ≥5 条「线上问题 → 根因 → 修复」记录）
- D5：成本优化冲刺（语义缓存 / 模型分流 / 批处理）+ DoD 逐条自评
- **合流点**：capstone 从"能跑"变成"敢给别人用"
- **检查点**：DoD 九条逐项达标或明确标注缺口；有压测 + 混沌 + 安全三份报告

### Week 12：框架提取、文档与面试（P0）

- D1：从产品中提取框架公共接口（只保留被真实使用过的抽象）+ 依赖注入
- D2：脚手架 `agent create` + 单元测试补全 + 本地打包
- D3：文档：架构图 + ADR ≥ 5 + README（指标 / 截图 / demo 视频）
- D4：前沿调研笔记（MCP/A2A/AG-UI、多智能体、Computer Use、上下文工程）+ 可落地评估
- D5：模拟面试：按两份 JD 十条职责逐条 10 分钟讲述
- **检查点**：第三方场景可用脚手架 1 天内跑通；能对着 JD 逐条讲清架构与量化结果

## 七、可选项清单（P3 · 默认档必做 / 深入档待解锁，由你最终判断）

> 这 6 项**都已排进计划**，区别只在深度：**默认档**保证"作品不缺环"，**深入档**是需要余量才解锁的加分项。判断权在你——下面给出成本、最佳挂载点和解锁信号，方便你按当时的实际余量决定。

| # | 项目 | 默认档（必做） | 深入档（可选） | 最佳挂载点 | 深入的边际收益 |
|---|---|---|---|---|---|
| 1 | 前端 | 单页 HTML + SSE 流式渲染（0.5 天） | 任务看板 + trace 可视化 + Next.js 部署（3–5 天） | W11 末 / W12 | 高：demo 观感最直观，招聘方看 5 分钟视频时最买账 |
| 2 | 多语言 | prompt 加 locale 参数，中英双版（0.5 天） | 术语表 + 文化适配 + 多语言评测集（2–3 天） | W10（内容生成周） | 中高：跨境增长是真实需求，还能扩展 golden set 维度 |
| 3 | A2A 协议 | 读规范 + 一次跨进程 handoff demo（0.5 天） | Agent Card / task lifecycle / 跨框架互通 / 与 MCP 分层对比（3–4 天） | W9（多智能体周） | 中：27% JD 提及，讲协议分层加分，但落地案例少 |
| 4 | Computer Use | 只写进 W12 前沿笔记（0） | 浏览器工具 + 沙箱 + 视觉定位 + 失败恢复（5–7 天） | 不建议 12 周内 | 低-中：强依赖目标岗位，通用岗性价比低 |
| 5 | 向量库 / 模型 | 用 pgvector，不造轮子（0） | 自研 HNSW 检索（3–5 天）/ LoRA 微调 router 分类器（5–10 天） | W12 之后 | 低：除非投基础设施或算法岗 |
| 6 | 高并发规模 | 100 并发压测 + 限流降级（已在 W2 / W11 内） | K8s + HPA + 多副本一致性 + 网关，压到 1000 并发（5+ 天） | W12 之后 | 中：证明工程深度，但与 Agent 岗位核心关联偏弱 |

**ROI 排序（每小时收益）**：A2A 轻量 > 多语言 > 前端极简 > 高并发 > 向量库/微调 > Computer Use

**解锁规则（防止"什么都想深入"把主线拖崩）**：

- 三个决策点：**W4 末、W8 末、W12 末**，只看一个指标——进度余量（落后/领先天数 × 3h）
- 余量 ≥ 15h 才解锁**一个**深入档；一次只开一个，做完再判断下一个
- 解锁顺序按上面的 ROI 排序，不按当时的兴趣
- 无论是否解锁，**默认档一律完成**——它们是"作品完整度"的地板，不是可选项

**各自的解锁信号（出现这些情况才值得深入）**：

- **前端**：需要现场 demo 且网络环境不确定 → 自托管单页比直播跑 CLI 稳得多
- **多语言**：目标 JD 出现"出海 / 跨境 / 多语言" → 直接做，性价比最高
- **A2A**：岗位涉及平台化或多 Agent 协作，且你 W9 的单/多 Agent 对比数据已有说服力 → 顺势做
- **Computer Use**：明确投"通用 Agent / 浏览器 Agent"方向 → 否则只写笔记
- **向量库 / 微调**：明确投基础设施或算法岗 → 否则跳过
- **高并发规模**：JD 明确写"高并发 / 大规模" → 否则用 W2 的 100 并发报告足够

## 八、风险与应对

- **落后风险**：任何一周拖延，先冻结第七节的「深入档」（默认档仍保留），**不砍每周合流与评测**——曲线断了，作品故事就断了。
- **外部依赖风险**：搜索/抓取 API 不稳定且有成本 → W8 起就用录制回放（record/replay）做离线可复现，评测不受外部波动影响。
- **过度设计风险**：框架层只写产品真实用到的抽象，宁可 W12 再提取，也不要 W1 就设计"通用框架"。
- **自我验收风险**：DoD 里的数字每周五更新，不靠感觉判断进度。
