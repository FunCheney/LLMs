## 3. 结论

1. **Gate「100 并发错误率 < 1%」离线档通过**：1224 请求 0 失败，且服务端 `error_code` 全为 `null`（不是"客户端没看见错"而是"根本没产生错"）。
2. **过载没有被误重试**：全部 994 条日志 `retry_count=0`，说明限流/背压在入口就拦住了，没有出现"503 触发重试风暴"的迹象（`ServerBusyError.retryable=False` 生效）。
3. **trace 已贯穿**：994 条记录 994 个不同 `trace_id` 与 `span_id`，无复用、无空值。
4. **`first_token_ms` p95 ≈ 32 ms**，但这是 mock 回放（fixture 直接返回预置帧），**只能证明埋点与链路口径正确，不能当真实延迟基线**。真实延迟必须等在线档。

## 4. 这些数字不能直接当基线的原因（必须记录的偏差）

- **客户端与服务端差了一个数量级**（locust p95 1200 ms vs 服务端 p95 35 ms）。差异不在应用：本次执行所在的机器在压测期间被外部调度反复暂停（locust 的 `-t 40s` 从 13:00:02 跑到 13:15:50，其中最后一个统计区间跨度达 926 s；`max 20 s` 的离群点全部出现在这些停顿窗口）。**延迟分位数请以服务端口径为准**，客户端口径只能相对比较。
- **RPS 只有 ~54**（`Requests/s` 聚合），远低于该端点能力。同样是环境停顿的结果，不代表实现上限。
- 因此本报告只把 **错误率 / retry / trace 三项** 当作有效结论；延迟与吞吐需要按下面的"待补"重跑。
