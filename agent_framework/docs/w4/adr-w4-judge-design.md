# ADR-W4-01 · Judge 设计：rubric 锚定、走 gateway、以及"一致性系数才是交付物"

- 状态：已采纳（2026-W47）
- 影响范围：`evals/judge/{rubric,llm_judge,stats}.py`、`evals/scripts/judge_agreement.py`
- 上游约束：ADR-004（业务层不直接 import provider）、ADR-009（alias 与 wire 名分离）

## 1. 问题

W3 的 `TaskMetrics.judge_score` 一直是 `null`。要把它填上，有两条路：

1. 直接用 `LLM` 给答案打 1–5 分，取均值；
2. 先定义**判据**（rubric），再用 LLM 按判据打分，并用人工标注**校验判据是否可复现**。

选 2。理由不是"更严谨"这种空话，而是一个可测的事实：路径 1 打出来的分数没有方差。
在没有锚定描述时，模型给 4 分是最"安全"的输出，54 条 case 会有 50 条落在 4 分，
均分 4.1，趋势图是一条直线。**一个没有方差的指标，无法支撑任何"改进了"的结论。**

## 2. 决策

### D1 分值必须有文字锚，且只允许整数

每个维度在 1/3/5 上各写一段**可观察的行为描述**，而不是形容词：

| 维度（权重） | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 事实准确（0.40） | 存在明确的事实错误，会把读者引向错误做法 | 主体正确，但有一处细节不严谨 | 全部事实陈述成立，且没有含糊的兜底说法 |
| 引用支撑（0.25） | 引用了不存在的来源，或把推断说成既定事实 | 结论方向一致，但有一处在引用里找不到对应 | 每条关键结论都能在引用中找到对应 |
| 覆盖度（0.20） | 答非所问，或只重复了问题 | 覆盖主问题，缺 1 个次要子问题 | 主问题与全部次要子问题都有回答 |
| 简洁（0.15） | 大段与问题无关的内容 | 有 1–2 句可删的铺垫 | 每句话都在推进答案 |

只允许整数：人工标注做不到小数点后一位，允许 4.3 分就等于让一致性系数无定义。
2/4 分由"介于两档之间"隐含，不单独写——写全 5 档会让 prompt 长一倍，而模型对
相邻档的分辨力并没有变好。

### D2 走 `LLMGateway`，alias 从路由表读

```python
self._alias = alias or gateway.catalog.routes["strong"].primary
```

不写死 `claude-sonnet-4-6`。写死的后果不是跑不起来，而是**换模型后分数整体漂移，
报告上只写"质量下降"**。同理，`judge_alias` 落进每份报告，让读者能自己判断
"这次 judge 和被评模型是不是同一家"——同源模型会系统性偏好自己的措辞风格
（self-preference bias），这是 judge 设计里最容易被追问的一点。

### D3 temperature 恒 0，但**不承诺确定性**

温度 0 把方差压到可测，去不掉全部随机性（上游浮点非确定性仍在）。
所以 `judge_agreement.py` 用的是"系数是否达标"，而不是"两次打分是否完全相同"。

### D4 解析失败必须降级，不许补分

`parse_judge_payload` 对四种情况明确报错：不是 JSON、缺 `scores`、缺维度/多维度、
分值非整数或越界。失败时 `JudgeResult.parse_error` 非空、`overall=None`，
由上层算作 judge 不可用。

**为什么不补一个中间分**："评不了"和"评了 3 分"在报告里是两件事。前者说明 judge
链路坏了（该修管道），后者说明答案一般（该改 prompt）。混同的后果是 judge 的故障
伪装成质量下降——团队会去调一个没坏的 prompt。

### D5 一致性系数是交付物，不是附赠品

`judge_agreement.py` 输出三个数（二次加权 kappa / 三档名义 kappa / Spearman）
+ 分布 + 逐条对照。门禁看**名义 kappa**（更严，不被"相邻档宽容"救回来）。

低于阈值时的处置顺序写进了报告：改锚 → 改维度的 `question` → 复核标注。
**不是调温度**：温度只会让分数更随机，不会让它更对。

## 3. 实测：规则基线的地板是 0.35 / 0.13

离线档没有 key，跑的是 `HeuristicJudge`（关键词规则基线）。24 条人工标注的结果：

| 指标 | 值 |
|---|---|
| 二次加权 kappa | **0.343** |
| 三档名义 kappa | **0.200** |
| Spearman | 0.437 |
| MAE | 1.167 |

**结论是负面的，这恰恰是它的价值**：

1. 名义 kappa 0.20 ≈ 略好于随机。规则基线**从不给出 1–2 分**——因为"事实错误"
   在词面上往往比正确答案更"像"一个答案（`MCP 是一种模型压缩方法` 里 MCP 这个词
   出现得好好的）。**关键词匹配判不了事实**，这是结构性的，不是调参能救的。
2. 第一版用的是中文二元切片，二次加权 kappa 只有 **0.075**（纯随机）。改成
   "去停用字后的单字集合"才到 0.347：改写后的答案几乎不会复用问题里连续两个字，
   二元覆盖率恒低，分数退化成"答案长度分"。这条弯路记在这里，避免下次有人再走。
3. 所以：**任何 LLM judge 的二次加权 kappa 必须显著高于 0.34、名义 kappa 高于 0.20，
   否则不如直接用规则**。
   这条地板现在有了具体数字，Gate 1 的判定不再靠感觉。

## 5. 成本预算

judge 一次调用约 600–900 prompt token + 150 output token。按 strong tier
（`claude-sonnet-4-6`，3/15 USD 每百万）算，**单条评测约 0.4 美分，54 条约 0.2 美元**，
占整次评测成本的大头（被测模型是 cheap tier）——所以 `run_eval` 默认不开 judge，
只有 `--judge` 显式打开，且报告里单列 `judge_cost` 与 `judge_alias`。
