# 案例 2 · 一个 p95 混了四种调用形态：2.45ms 里没有一条是"聊天变慢"

- 日期：2026-W47 · 归因层：**指标口径层**（可观测）
- 涉及文件：`evals/metrics.py::by_kind`、`evals/scripts/run_eval.py`（报告分栏 + 快照 `by_kind`）

## 1. 现象

W46/W47 两期报告的"延迟"一行：

```
| 延迟 | latency p50 / p95 | 0.2ms / 2.45ms | 50 |
```

W46 是 `0.16ms / 2.29ms`，W47 是 `0.18ms / 2.45ms`。连续两期都是"p95 是 p50 的十倍以上"，
看起来像"有一批请求很慢"。但翻 `cases[]` 会发现：**没有任何一条 case 的延迟接近 2.45ms**。

## 2. 根因

`aggregate()` 把所有拿到 `RequestLog` 的样本丢进同一个列表算分位，而 54 条 case 里
混着四种形态：

| kind | 条数 | 干什么 |
|---|---|---|
| `chat` | 12 | 一次性返回 |
| `stream` | 4 | 逐帧吐字，total latency 含整段生成 |
| `tool_call` | 12 | 返回工具调用（不生成正文） |
| `error` | 4 | 故意 429/5xx，**要跑重试退避** |

`error` 类的 p50 是 **3.95ms**（重试退避睡的），`stream` 的 p50 是 0.43ms，`chat` 是 0.18ms。
把它们混在一起算 p95，得到的 2.45ms 是四个分布的混合分位 ——
**它既不代表聊天体验，也不代表流式体验，只代表"我们把四种东西搅在了一起"。**

更糟的是它的误导方向：读者看到 p95 从 2.29 涨到 2.45，会去查"哪个 chat 请求变慢了"，
而真实变化来自 JIT 与进程调度，与聊天链路无关。

## 3. 改动

1. `metrics.by_kind(results)`：按 `kind` 分组聚合（与 `by_difficulty`/`by_tag` 同构）。
2. 报告的"难度与标签分布"之后新增一节：

   ```
   ### 按调用形态拆延迟（chat 与 stream 不是一个分布）
   | kind | 条数 | latency p50 | latency p95 | 样本 |
   ```

3. 快照写入 `by_kind`，供趋势图与 W11 看板按形态取数。
4. **合计数保留不动**（它仍有意义：整体 SLO），但报告里必须同时给出分解 ——
   一个数字单独出现时，读者只能靠猜。

## 4. 量化改进

W47 同一批 50 个样本，改动前后（数据来自 `evals/history/2026-W47-eval.json`）：

| 视图 | p50 | p95 | 样本 |
|---|---|---|---|
| 改动前（混合） | 0.18ms | **2.45ms** | 50 |
| chat | 0.18ms | **0.47ms** | 12 |
| tool_call | 0.21ms | 0.74ms | 12 |
| stream | 0.43ms | null（4 样本，不足 5 条不报 p95） | 4 |
| error | 3.95ms | null（4 样本） | 4 |
| draft | 0.12ms | 0.21ms | 8 |
| research | 0.13ms | 0.18ms | 10 |

结论：混合 p95（2.45ms）是 chat p95（0.47ms）的 **5.2 倍**，误差量级 420%；
混合值主要由 4 条 `error` case（故意重试退避）抬起来。

## 5. 取舍与遗留

- 取舍：分层后每条线样本变少（`stream`/`error` 各 4 条），**p95 按规则返回 null**。
  这是有意的：4 个点算 p95 只是把最大值改了个名字。要看流式 p95，必须把流式样本补到 ≥5 条。
- 遗留：`stream` 的 `first_token_ms` 才是 SLO 该看的数（W2 压测已确立），
  但离线夹具只有 4 条流式 case；`first_token_p50 = 0.37ms` 目前只够"证明埋点在"。
- 遗留：`error` case 的延迟理应**从延迟统计里剔除**（它衡量的是我们故意制造的失败）。
  本次只做了分层、未做剔除——剔除会让"重试退避把用户等多久"这个信息消失，
  等 W11 讨论 SLO 定义时再定。
