# ADR-W9-001：编排范式选型——capstone 五条链路逐条判定

- 状态：已采纳（W9 D1）
- 日期：2026-11-12
- 相关：`planner/{react,plan_execute,research_planner,controls}.py`、ADR-W9-002（多智能体）、`docs/w9/single-vs-multi-ab.md`（实测）

---

## 背景

"Agent"这个词在工程上最常见的用法是**过度使用**。同一件事有三种写法：

```python
# 脚本：20 行，确定性，可测
outline = template(keyword)

# Workflow：步骤固定，每步可单测
outline = await outline_step(keyword)

# Agent：模型决定下一步
result = await planner.run(f"给 {keyword} 写大纲")
```

第三种在 demo 里最惊艳，在生产里最贵：本来 20 行确定性代码能保证的事，交给模型后
变成"通常能行"。所以这份 ADR 的第一件事不是论证我们选了哪种范式，而是
**把 capstone 的每条链路都判一遍形态**——写错范式的返工成本最高，一旦按
Agent Loop 写完再退回 Workflow，等于重写。

---

## 决策

### 1. 判据表（出现就选它）

| 形态 | 判据 | 关键代价 |
|---|---|---|
| 脚本 | 步骤可枚举且无判断 | 无 |
| Chatbot | 不需要工具、不需要记忆 | 无 |
| RAG | 答案在文档里且**一次召回可得** | 召回错了就错 |
| Workflow（固定图） | 步骤顺序几乎不变 | 改流程要改代码 |
| Workflow（Routing） | 任务类型可先分类 | 分类器本身会错 |
| Workflow（Evaluator-Optimizer） | **能写出评分函数** | 评分为 0 时无解 |
| Workflow（Orchestrator-Workers） | 子任务同构且可并行 | 汇总层要处理冲突 |
| Autonomous（ReAct / P&E） | **下一步依赖上一步结果** | 成本与延迟不可预知 |
| 多 Agent Graph | 单 Agent 上下文放不下，或需要角色隔离 | 协调开销 + 状态一致性 |

### 2. capstone 五条链路逐条判定

| # | 链路 | 判定 | 理由（为什么**不是**更"高级"的那个） |
|---|---|---|---|
| 1 | 关键词清洗 / 字数裁剪 / 分句 | **脚本** | 规则明确、输入结构固定。用模型做等于用一个会撒谎的字符串函数 |
| 2 | 品牌客服问答（FAQ 命中） | **Chatbot + 小 RAG** | 答案就在 FAQ 里，一次召回可得。不需要"决定查什么" |
| 3 | 竞品卖点提取（"这个竞品主打什么"） | **RAG** | 答案在文档里。检索一次就够，规划只会多花两步 |
| 4 | SEO 流水线（关键词 → 大纲 → 成文 → meta） | **Workflow（固定图）** | 步骤顺序几乎不变。让模型决定"先写大纲还是先查词"是给系统加随机性 |
| 5 | 深度调研（搜什么取决于搜到啥） | **Autonomous（P&E + Agentic Search）**，复杂时升级为**多 Agent** | **唯一**满足"下一步依赖上一步结果"的链路 |

**结论：五条里只有第 5 条真的需要自主性，其余四条都是确定性编排。**
所以 W9 做 Plan-and-Execute，但**不把整条链路都改成 Agent**——W10 的 SEO 流水线
仍然是固定 Workflow。

第 4 条特别值得写下来：它有一个"看起来该用 Agent"的诱惑（选题类型不同，
写不同的模板）。那是 **Routing**，不是 Autonomous——先分类再走固定分支，
比让模型边写边决定便宜一个数量级。

### 3. 什么时候**不该**用 Agent（五条红旗）

出现任意两条，就应该退回 Workflow：

1. **能写出确定的判分函数**——说明"好不好"是可判定的，那就用 Evaluator-Optimizer，
   不需要模型自己决定何时停。
2. **步骤可以提前枚举**——说明路径是固定的，那就画图。
3. **失败代价高且难回滚**——自主性意味着可能走错路，走错要能撤。
   撤不回来的动作（发布、付款）必须由人批（控制权矩阵"是否发布"归 human）。
4. **成本必须可预测**——Agent 的成本是分布不是数字。要按量报价的产品，
   用 Workflow 才能给出上限。
5. **同一步骤要跑 1000 次**——Agent 的第 1000 次和第 1 次可能不同，
   而 Workflow 的第 1000 次与第 1 次可复现。批量任务里，可复现 > 聪明。

### 4. 为什么主线选 Plan-and-Execute，而不是 ReAct

| | ReAct | Plan-and-Execute | 本项目的选择 |
|---|---|---|---|
| 状态 | 只有观察窗口 | 计划 + 观察窗口 | P&E |
| 长任务 | 窗口一满就丢早期信息 | 计划本身承担"我在哪" | P&E |
| 可审计 | "为什么走这一步"只能从日志倒推 | 计划是可读的产物，可提前给人看 | P&E |
| 灵活度 | 高（每步都可改主意） | 低（改主意要重规划） | ReAct 作为对照组保留 |

两个都实现是硬要求：没有 ReAct 基线，"P&E 更好"没有对照。

> **但 D5 的实测给了一个不好听的结论**：在 5 步任务上，P&E 与 ReAct 的差距
> **完全由观察窗口解释**，不来自"有计划"——`plan_execute_w3`（窗口 3）与
> `react_w3` 得分一样低（0.80），`plan_execute_w8` 与 `react_w8` 一样高（1.00）。
> 见 `single-vs-multi-ab.md` §3。所以上表"长任务 P&E 更好"这句，
> **在当前证据下应该改成**："P&E 让窗口可以开小而不失控，因为计划承担了记忆；
> 但如果窗口本来够大，两者没有差别。"

### 5. 为什么深度调研用 Agentic Search 而不是 RAG

第 5 条链路是"搜什么取决于搜到啥"。RAG 的形态是"把问题向量化 → 取 top-k → 生成"，
它假定**一次召回就够**。深度调研不满足这个假定：

- 一个问题要拆成 3–5 个正交子问题（定义 / 规模 / 竞品 / 风险），
  一次 top-k 召回会把四类证据混在一个嵌入空间里，往往每一类都只召回一半；
- 搜到什么决定了下一步搜什么（缺"风险"就去补"风险"），这是**循环**不是**流水线**；
- 什么时候停取决于"边际收益"，而这只能在跑的过程中观测。

所以 D2 的 `ResearchPlanner` 是循环 + 缺口（`Gap`）+ 预算（`SearchBudget`），
四个停止原因都能单独断言：`enough_evidence` / `search_budget` /
`low_marginal_yield` / `duplicate_query`。

### 6. 控制权矩阵：模型只拿 3 个决定

| 决定 | 归属 | 为什么 |
|---|---|---|
| 下一步做什么 | model | 这是 Agent 的本职 |
| 调用哪个工具 | model | 同上 |
| 工具参数 | model | 同上 |
| 工具是否可见 | **code** | 模型不该知道自己看不见的工具，更不能"申请"看见 |
| 是否能继续 | **code** | 预算/步数/环路；模型说"还能继续"不作数 |
| 是否越过权限 | **code** | 模型自评"我有权限"是最危险的一类幻觉 |
| 是否发布 | **human** | 对外动作，W10 接 HITL |

**未登记的决定默认归 `code`**（`ControlMatrix.owner_of`）。反过来的默认值
（归模型）会让新增决定悄悄扩大模型权限，而没人会注意到。

> 修正一处文档与代码的不一致：`w9-tasks.md` 的正文写"模型只拿到 2 个"，
> 但同一页的表里列了 3 个 model 行。**以代码为准：3 个。** 这种"表格与正文
> 各说一套"的地方必须当场钉死，否则以后引用时会引用到错的那个。

矩阵不是文档里的一段话：`StepRunner.__init__` 会调 `assert_code_owned`，
`visible_tools()` 查 `owner_of("工具是否可见")`，`run()` 查 `model_may_decide`，
`PlannerBase._check_continue()` 查 `assert_code_owned("是否能继续")`。
`test_control_matrix_has_no_dead_entries` 扫源码盯这一点——**它红过一次**，
当时矩阵确实是装饰品，修法是把矩阵接进运行时，不是给测试加豁免。

## 后果

### 好的

- 五条链路各有判定，且**四条明确写了"不用 Agent"**——这份 ADR 的价值一半在拒绝。
- 两个对照组（ReAct / P&E）都在，D5 的对比才有基线。
- 控制权矩阵在运行时被查询，不是文档装饰。

### 代价

- **两套规划器要一起维护。** 共用 `PlannerBase` 把重复压到最小，但
  "ReAct 该不该补某个能力"的每次讨论都要问一遍"这会破坏对照组吗"。
  这是刻意保留的不对称：ReAct 保持朴素，它才有对照价值。
- **P&E 的可读计划是额外产物**，要有人看才有用。目前只有 trace 里有，
  没做"计划预览"的 UI。
- **矩阵里"是否发布"目前是占位**：W9 没有任何发布动作，`human` 这一格
  在 D3 的 `requires_human` 里被查询了一次，但真正的 HITL 在 W10。

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 整条 capstone 链路都做成 Agent | 五条里四条不需要；成本不可预测，且把确定性保证换成了"通常能行" |
| 只做 ReAct（省一个规划器） | 没有对照组，"P&E 更好"无从证明；且长任务上 ReAct 会输 |
| 只做 P&E（不写 ReAct） | 同上，D5 的一半结论会失去依据 |
| 用 LLM 决定"何时停" | 停下是最需要确定性的决定。预算归 code，归 model 等于把刹车交给油门 |
| 把控制权矩阵写成文档表格 | 文档不改代码。必须是代码常量 + 运行时查询 + 一条会红的测试 |
| 让 supervisor 也检索（省一层） | 它同时是调度方和写入方，读到的快照很快过期而自己感觉不到 |
