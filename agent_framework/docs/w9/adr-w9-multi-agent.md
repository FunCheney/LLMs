# ADR-W9-002：多智能体的拆与不拆、handoff 语义、预算模型

- 状态：已采纳（W9 D3）
- 日期：2026-11-12
- 相关：`multi_agent/{roles,handoff,shared_state,supervisor}.py`、`tests/test_multi_agent.py`、ADR-W9-001（规划器选型）、ADR-W9-003（LangGraph 对照，D4）

---

## 背景

D3 要做的是「多智能体」。这个词在 JD 里的出现频率远高于它能带来的收益，
所以这份 ADR 的第一件事不是论证怎么拆，而是**论证什么时候不拆**。

参照系是 W9 D1/D2 已有的两件东西：`PlanExecutePlanner`（单 Agent、有计划）
与 `ResearchPlanner`（单 Agent、多轮检索）。多 Agent 必须回答一个单 Agent
答不上的问题，否则它只是把一次调用拆成三次、把一份预算拆成三份。

多 Agent 真正换来的是两样东西：

1. **上下文隔离**：每个角色只看见自己要的那部分，窗口不被别人的中间产物污染；
2. **权限隔离**：不同角色可以被授予不同的工具集合（researcher 有检索、validator 没有写权限）。

换来的是三样代价：**协调开销**、**状态一致性**（并发写）、**成本放大**（每跳都要
重新建立上下文）。W9 的 supervisor 就是把这三样代价压到可接受的最小实现。

---

## 决策

### 1. 什么时候拆：四个判据，缺一不拆

| 判据 | 单 Agent 的形状 | 多 Agent 才成立 |
|---|---|---|
| 上下文超窗 | 中间产物超过窗口的 60% | 每个角色只需其中一段 |
| 权限不同 | 所有步骤同一主体同一权限 | 至少两个角色需要**不同**工具面 |
| 可并行 | 步骤线性依赖 | 至少两条子任务无依赖 |
| 需要对抗 | 一次生成、一次校对 | 校验方**必须**看不见生成方的推理过程 |

四条里只满足第一条，用 D2 的 `ResearchPlanner` 就够；只满足第四条，用一次
`critic` 调用就够。**四个都不满足还拆，就是纯粹的成本放大。**

W9 的实现满足第 2 与第 4 条：`researcher` 有 `web_search`、`validator` 没有；
`validator` 只看 `Finding.citation` 是否为空，看不见 `researcher` 为什么选这个问题。
第 1、3 条**不满足**——这是刻意的，写在这里是为了让 D5 的对比有解释力：
多 Agent 若在 W9 的样例上只是"不比单 Agent 差"，归因就是"这次拆分本来就不该拆"。

### 2. handoff 是**消息**，不是函数调用

`Handoff(from_role, to_role, task, artifacts, budget_left_tokens, step_no)`。
接收方可以拒绝（返回的 `RoleResult` 里可以什么动作都没有）。

三个字段的语义各有讲究：

- **`artifacts` 传 id，不传正文。** 传正文会让 handoff 悄悄变成第二条上下文通道：
  预算按 handoff 次数估，实际按正文长度花，两边立刻对不上。
- **`budget_left_tokens` 是剩余量，不是分配量。** 见 §3。
- **`step_no` 带着走**，但**不进指纹**。带着是为了让接收方知道"还剩几步"，
  进指纹会让每一跳都不一样（见 §4.1）。

### 3. 预算：一个数在递减，不是每跳重新赋值

```
总预算 20_000
  ├─ supervisor 派 researcher   budget_left = 20_000 - 已用
  ├─ supervisor 派 researcher   budget_left = 20_000 - 已用   ← 已用变了
  └─ supervisor 派 validator    budget_left = 20_000 - 已用
```

写错的样子是每个角色各拿 20_000：**看板上每一跳都显示"余额充足"，总额是配置值的 N 倍。**
这类 bug 不会报错，只会体现在账单上。

两个刻意的口径选择：

- **记账单位是角色申报的 token**（推理 + 检索成本），不是 `StepRecord.tokens`。
  后者是工具**输出**的估算——那不是我们付的钱，把它算进预算会让"工具话多"
  变成"预算超支"，账单对不上。`StepRecord.tokens` 只留在轨迹里给 D5 用。
- **两个上限不共用一个常量**：`SupervisorConfig.max_steps` 数"角色行动一轮"
  （可能含 3 次工具调用），`AutonomyBudget.max_steps` 数执行步数。混用会让
  两边的"步"含义不同，成本折算不回去。

### 4. 三道守卫，各防一种失败

| 守卫 | 防的是 | 触发后的样子 |
|---|---|---|
| 步数 | 角色膨胀 / 无限细化 | `stop_reason=max_steps` |
| 预算累计 | 每跳重置 | `stop_reason=max_tokens` |
| 环路指纹 | 两个角色互踢皮球 | `stop_reason=plan_loop` |

后加的两道是**测试逼出来的**，不是设计时想到的：

#### 4.1 环路指纹 = `(from, to, task)`，两种形态

```python
key = sha256(f"{from_role}\x00{to_role}\x00{task.strip()}")[:12]
```

- **不含 `step_no`**：每次都是新值，指纹永不重复，检测等于没有。
- **不含 `artifacts`**：把同一件事换个说法重问就逃掉了，而那正是要抓的。

两种形态都要抓：

1. **同边重复**：同一条 `(from,to,task)` 出现 ≥2 次（最常见）；
2. **两点来回**：`a→b→a→b`，四条边的指纹**各不相同**，只查第 1 种会漏。

`_find_cycle` 里有一行是踩出来的：**窗口内必须有两个以上不同角色**。
最初没有这个限制，两个子问题的正常流程在第 4 轮被判成环、报告只剩一半还标着
`plan_loop`——因为研究员连着被派（`[r,r]`）在序列上"重复"了。同一个角色连任
不是互踢皮球，那是它在逐个查子问题；调度器自己卡住归"无进展"与步数守卫管。

判环后**抛 `LoopDetected`**，不返回一个"你自己看着办"的标记：调用方只要写了
`record` 就没法忘了检查。触发的那条 handoff 留在流水里——它是证据。

#### 4.2 步数记"角色轮数"，不是工具调用次数

写错的样子：一个只说"我没有新问题可查"的角色不产出任何动作，
按工具调用计数则步数永远停在原地，**守卫永不触发而循环转得很欢**。
工具调用次数单独记在 `trace.records` 里，给 D5 的 `steps_used` 用，两者不是同一个数。

配套一条 `no_progress`：**同一个角色连着两轮空手**就停。判据必须是"连着两次"——
`validator` 判 `needs_fix` 时同样不产出任何东西，而它下一棒该交给 researcher。

### 5. 共享状态：乐观锁必须在**写入点**校验

```python
state.commit(role, findings=..., expected_version=snapshot)
```

并发「读-改-写」的失败模式：A 读到 v3，B 也读到 v3，A 写（v4），B 也基于 v3 算出 v4 写下去
——**B 的写入把 A 的覆盖了，而两边都以为成功**。这类丢失在日志里看不出来。

两条纪律：

- **不自动重试。** 重试会把"谁的工作被丢了"这个问题藏起来，而丢工作的人不会收到通知。
  supervisor 把它转成 `stop_reason=error` + 冲突详情，让值班的人看见。
- **`history` 记 `(version, role, added)`。** 排查"结论怎么变成这样"时要能倒放。

与 W6/W8 的幂等是同一条主线的另一面：那边防重复执行，这边防并发覆盖，
共同点是**乐观锁在写入点校验，不在读取点假设**。

### 6. 角色职责单一 = 角色**没有可越界的工具**

supervisor 的角色实现是 `SupervisorRole`，它只有 `pick()`，没有 `runner`、
没有 `executor`——想检索也没有工具可用。`act()` 直接抛 `NotImplementedError`。
这条约束让版本冲突的范围缩小一半：只有 researcher 与 validator 会写状态。

"职责单一"如果只写在文档里，第一次赶工就会被破。所以 `test_supervisor_role_has_no_tools`
断言它压根没有可调用的东西。

角色返回的是**意图**（`RoleAction`），不是结果：真正调工具的是 W8 的 `StepRunner`
（五道门都在那里）。角色自己写状态会出现「工具失败了但状态已经更新」的鬼故事。

## 后果

### 好的

- 三道守卫**都有反向用例**：构造触发条件，断言返回 `partial`/`aborted` 而不是完整结果。
  没有反向用例的守卫，等于文档里的一句话。
- 预算、步数、环路各自有独立的停止原因（`max_tokens` / `max_steps` / `plan_loop`），
  **可归因**。全部报 `unknown` 的话，这次运行就没法写进趋势。
- 有半成品时返回 `partial` 而不是 `aborted`：报告的 4/5 也是价值，产品文案依赖这个区别。
- 角色边界可测（没有属性可查），不是靠 code review 守。

### 代价

- **每次 handoff 都重建上下文。** 同一份任务，角色越多、轮数越多，token 越高——
  具体高多少由 D5 量（`docs/w9/single-vs-multi-ab.md`），**这里不预先给数**。
  这是拆分本身的成本，不是实现缺陷。
- **`Supervisor` 仍然知道角色名。** `_ask_for()` 里对 `ROLE_RESEARCHER` / `ROLE_VALIDATOR`
  做了特判（生成带轮次 vs 恒定的子任务描述）。这层耦合是为了让指纹能区分
  "换个子问题再查"与"同一件事重问"。新增第四种角色时要记得加一行，否则它会拿到
  恒定的 task 描述，连着派两次就被判环。**这是已知的扩展点，不是隐藏坑。**
- **没有真正的并行。** 三个角色是顺序 await 的。`SharedState` 的版本号机制是为并行
  准备的（D5 之后若要接 `asyncio.gather`，`expected_version` 已经在写入点校验了），
  但 W9 没有跑过真正的并行，`test_supervisor_reports_conflict_instead_of_dropping_it`
  用"在 `act` 里抢先 commit"来模拟。**这一点必须在验收里写明是模拟。**

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 用 `langgraph` 作主实现 | 守卫会在框架的节点/边里散开，说不清"预算在哪一层扣"。D4 用同一张图做对照，量这个差异 |
| handoff 传完整正文 | 第二条上下文通道，预算按次数估、按长度花，必然对不上 |
| 预算每跳重置（"每个角色一份额度"） | 总成本 ×N，而看板上每跳都显示余额充足 |
| 环路检测只看同边重复 | 漏掉 `a→b→a→b`（每条边只出现一次）这个最典型的形态 |
| 环路检测用通用图环算法 | 真实的互踢皮球是 2–3 个角色在小范围来回；长度 >4 的"环"已经是正常长流程，抓它只误报 |
| 版本冲突自动重试一次 | 会掩盖"谁的工作被丢了"；且重试会重复已经发生的副作用 |
| 让 supervisor 也顺手检索 | 它同时是调度方和写入方，读到的快照很快就过期而自己感觉不到 |
| 用 `success: bool` 表达结果 | 表达不了 `partial` 与 `aborted` 的差别，而产品文案完全依赖它 |
