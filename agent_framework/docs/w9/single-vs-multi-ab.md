# 单 Agent vs 多 Agent：三层对比（Outcome / Trajectory / System）

- 日期：2026-11-12（W9 D5）
- 实验脚本：`evals/scripts/agent_paradigm_ab.py`（可原地重跑）
- 指标层：`evals/scripts/trajectory_eval.py`（18 条口径单测）
- 任务集：`evals/golden/w9_agent_v1.jsonl`（6 条：3 简单 + 3 复杂）
- 原始数据：`evals/history/2026-W52.json` 的 `w9_ab` 块

---

## 0. 结论先行

1. **在这批任务上，多 Agent 没有带来"分工收益"，一分钱都没有。**
2. 差异**全部**由**记忆机制**解释：证据是"窗口够就赢、窗口不够就输"，与用哪种范式无关。
   - `react_w8` = `plan_execute_w8` = `multi_agent` = **1.00**
   - `react_w3` = `plan_execute_w3` = **0.80**
3. `Plan-and-Execute` 的"计划"**没有救它**：小窗口下它和 ReAct 一样掉到 0.80。
   它的优势来自"默认窗口更宽"（8 vs 3），不来自"有计划"。
4. 过程层抓到了结果层看不见的东西：`react_w8_noisy` 覆盖率与 `react_w8` 相同（1.00），
   但**多花一步**（6 vs 5）——结果一样，过程更贵。

第 1、2 条合起来是一句更难听但更有用的话：**"多 Agent 更好"在这里等价于
"共享状态不受窗口限制更好"。** 如果只是想让 Agent 记住更早的东西，把窗口开大就行，
不必拆多 Agent。

## 1. 实验设置

### 1.1 任务集

| 档 | 条数 | 形状 |
|---|---|---|
| 简单（difficulty 1/2） | 3 | 1 步：查一次就有答案 |
| 复杂（difficulty 3） | 3 | 5 步，**第 5 步要回忆第 1 步的结论** |

`recall_from` 是任务集里唯一的机关：它把"上下文窗口够不够"变成一个可测变量。
回忆距离刻意设成 **4 步**——窗口 1 与窗口 3 都够不着，窗口 8 够得着。

> 踩过一次：最初始的版本是 3 步、回忆距离 2，四种编排**全部 1.00**。
> 原因是默认窗口 3 在 3 步任务里刚好够用。没有区分度的实验比没有实验更危险：
> 它会让人以为"验过了，没问题"。

### 1.2 任务世界（确定性、无网络）

`PolicySearch` 只认精确查询，三种返回：

1. 查询匹配到某一步 → 返回该步的真值（`值0`…`值4`）；
2. 是复核步但没把要复核的值带进来 → 返回一个**看起来正常但内容错**的结论（`无结论N`）；
3. 完全匹配不上（模型编了个查询）→ 空结果。

第 2 条是这套实验的物理定律：**工具调用成功了，答案却是错的。**
线上最常见的失败形态就是这个，它比抛异常难发现得多。

### 1.3 七个配置

| 配置 | 编排 | 窗口 | 为什么有它 |
|---|---|---|---|
| `react_w1` | ReAct | 1 | 剂量曲线低点 |
| `react_w3` | ReAct | 3（默认） | 默认配置对照 |
| `react_w8` | ReAct | 8 | **归因关键**：只改窗口，不改范式 |
| `plan_execute_w3` | Plan-and-Execute | 3 | **归因关键**：只改范式，不改窗口 |
| `plan_execute_w8` | Plan-and-Execute | 8（默认） | 默认配置对照 |
| `react_w8_noisy` | ReAct | 8 | 过程层探针：让模型选错一次工具 |
| `multi_agent` | Supervisor（researcher + validator） | 无（共享状态） | 本体 |

`react_w8` 与 `plan_execute_w3` 这两档是整个实验的核心：它们把"范式"与"窗口"
拆成两个独立变量。只比 ReAct(3) 与多 Agent 的话，窗口的功劳会被记在"分工"头上。

## 2. 三层指标（全量实跑）

### 2.1 简单档（difficulty 1/2，3 条）

| 配置 | Outcome 覆盖 | 工具选择 | 无效调用 | 步数 | 路径重复 | token |
|---|---|---|---|---|---|---|
| `react_w1` | 1.00 | 1.00 | 0.00 | 1.00 | 0.00 | 220 |
| `react_w3` | 1.00 | 1.00 | 0.00 | 1.00 | 0.00 | 220 |
| `react_w8` | 1.00 | 1.00 | 0.00 | 1.00 | 0.00 | 220 |
| `plan_execute_w3` | 1.00 | 1.00 | 0.00 | 1.00 | 0.00 | 220 |
| `plan_execute_w8` | 1.00 | 1.00 | 0.00 | 1.00 | 0.00 | 220 |
| `react_w8_noisy` | 1.00 | 1.00 | 0.00 | **2.00** | 0.00 | 344 |
| `multi_agent` | 1.00 | 1.00 | 0.00 | 1.00 | 0.00 | 37 |

简单档全部打平——**这是预期内的**：单步任务没有"记忆"这个变量。
打平本身有意义：它说明这批配置在简单任务上不该被"多 Agent 更聪明"的说法解释。

### 2.2 复杂档（difficulty 3，9 条 = 3 case × 3 trials）

| 配置 | Outcome 覆盖 | 工具选择 | 无效调用 | 步数 | 路径重复 | token |
|---|---|---|---|---|---|---|
| `react_w1` | **0.80** | 1.00 | 0.00 | 5.00 | 0.00 | 926 |
| `react_w3` | **0.80** | 1.00 | 0.00 | 5.00 | 0.00 | 926 |
| `react_w8` | **1.00** | 1.00 | 0.00 | 5.00 | 0.00 | 925 |
| `plan_execute_w3` | **0.80** | 1.00 | 0.00 | 5.00 | 0.00 | 926 |
| `plan_execute_w8` | **1.00** | 1.00 | 0.00 | 5.00 | 0.00 | 925 |
| `react_w8_noisy` | **1.00** | 1.00 | **0.17** | **6.00** | 0.00 | 1049 |
| `multi_agent` | **1.00** | 1.00 | 0.00 | 5.00 | 0.00 | 139 |

0.80 的构成：5 步里丢掉第 5 步（复核步）——它的查询里带"未知"而不是记住的值，
于是工具返回了 `无结论4`。**报告仍然写着"结论：值4"**（这是 `PolicyReasoner.compose`
按任务书合成的，见 §5 局限 3），也就是"看起来圆满、实际少了一条证据"。

### 2.3 Multi-Trial（复杂档，每配置 3 次）

| 配置 | 覆盖均值 | 极差 | token 均值 | token 极差 |
|---|---|---|---|---|
| `react_w1` | 0.80 | **0.00** | 926 | 0 |
| `react_w3` | 0.80 | **0.00** | 926 | 0 |
| `react_w8` | 1.00 | **0.00** | 925 | 0 |
| `plan_execute_w3` | 0.80 | **0.00** | 926 | 0 |
| `plan_execute_w8` | 1.00 | **0.00** | 925 | 0 |
| `react_w8_noisy` | 1.00 | **0.00** | 1049 | 0 |
| `multi_agent` | 1.00 | **0.00** | 139 | 0 |

**极差恒为 0，这个数必须解释清楚，不能当成"很稳"。**

离线档的任务世界是确定性的（精确查询匹配、策略无随机），所以 3 次重复**必然**同值。
它证明的是**可复现**（同一份输入 → 同一份输出），**不是稳定性**。
真正的稳定性要看在线档（`LLMReasoner` + 真模型）的 3 次极差——**本次没有跑**，
因为没有可用 key，也不该为了让表格好看去凑一个数。

> 这条是本报告最容易被读歪的地方：一张"极差 0.00"的表，读者第一眼会读成
> "系统非常稳定"。它不是那个意思。

## 3. 归因到层：差异到底来自哪里

用三个对照把变量分开：

| 对照 | 变了什么 | 覆盖率变化 | 说明 |
|---|---|---|---|
| `react_w3` → `react_w8` | **只**改窗口 | 0.80 → 1.00 | 窗口是充分条件 |
| `react_w3` → `plan_execute_w3` | **只**改范式（同样小窗口） | 0.80 → 0.80 | 范式在窗口不够时**毫无帮助** |
| `react_w8` → `multi_agent` | 换成共享状态 | 1.00 → 1.00 | 多 Agent 没比"窗口够"更好 |
| `plan_execute_w3` → `plan_execute_w8` | 只改窗口 | 0.80 → 1.00 | P&E 的优势也在窗口 |

**归因结论（能说清的）：**

- 本批任务的得分差异 **100% 由"记忆机制"解释**：窗口 ≥ 回忆距离 → 1.00，
  否则 → 0.80。这是一个阈值效应，不是渐变。
- "是否分工"（ReAct / P&E / 多 Agent）**没有可观测贡献**。
- 多 Agent 之所以到 1.00，因为共享状态**不受窗口限制**——它等价于"窗口无限大"。

**归因结论（说不清的，如实写）：**

- 多 Agent 的 1.00 **不**等于"多 Agent 范式更好"。它只证明了"共享状态比窗口能装"。
  要证明分工本身有价值，需要"多个角色各自需要不同工具面/权限"的任务，
  **本任务集没有这种任务**（全部只用 `web_search`）。
- 因此"什么时候值得拆多 Agent"这个问题，本次实验**只回答了一半**：
  能回答"只为了记性而拆，不值得"；不能回答"为了权限隔离而拆，值不值得"。

## 4. 过程层抓到了什么（结果层看不见的）

`react_w8_noisy` 与 `react_w8` 的覆盖率、工具选择准确率**完全相同**（1.00），
但：

- **步数 6.00 vs 5.00**：那次"编了个不存在的工具（`web_search_v2`）"被 W8 的门挡下，
  然后重试，多花一步；
- **无效调用率 0.17 vs 0.00**：6 步里有 1 次被自己的门挡住。

这正是过程层存在的理由：**只看结果，这两档一模一样；看过程，一档在交学费。**
如果这类失败率随模型变差而上升，结果层要等到它把正确率拖下来才看得见，
那时已经在处理"为什么最近变差"，而不是"这一版提示词让工具选择变差了"。

一个口径细节：`tool_selection_acc` 对"多调了"**不敏感**（LCS 口径，多调一次不算选错），
所以它在 noisy 档仍是 1.00。这不是漏，是分工：**多调不算错，"调错了"由
`invalid_call_rate` 抓。** 两个指标各管一件事，不互相顶替。

同时它也有一个真实局限（写进单测）：LCS 对**换序**扣分（`[a,b]` vs `[b,a]` 得 0.5）。
对工具顺序有语义的任务这是对的；对无顺序任务应该换集合覆盖率，而不是改口径。

## 5. 局限（读结论前必须看）

1. **离线档是确定性的。** 极差 0.00 = 可复现，不是稳定。在线档未跑。
2. **token 列不能跨档比较。** 单 Agent 记的是"reasoner 每次调用的申报成本 + 工具输出估算"，
   多 Agent 只记"角色申报的成本"，supervisor 与 validator 的推理成本**没有计**。
   所以 `multi_agent = 139` 不代表它便宜，只代表**它的账算少了**。
   真实成本对比需要在线档的统一计价（W11 的成本看板）。
3. **离线档的答案文本不能当 outcome。** `PolicyReasoner.compose` 是按任务书合成的，
   报告里天然有每一步的真值——用它判覆盖，七档会全部 1.00（实测过）。
   所以本报告的 Outcome 判据是"**证据有没有真的取回来**"，不是"答案文本对不对"。
   在线档才有资格判答案。
4. **多 Agent 档的检索词是我们替它构造的**：用的是"有完整共享状态时本应提出的词"。
   真实系统里这个查询由模型用共享状态生成，会引入新的失败面。所以 1.00 是它的
   **能力上限**，不是它的实测水平。
5. **任务集只用了一个工具**（`web_search`）。"选错成另一个合法工具"这类失败测不出来，
   因为它不存在。
6. **结论不可外推成"多 Agent 无用"。** 它只覆盖"记忆机制"这一个变量。
   权限隔离、上下文隔离、对抗式校验这三条（ADR-W9-002 §1 的另外三条判据）
   本任务集一条都没测。
7. **样本量小**：复杂档 3 条 × 3 次。结论是"机制层面的定性判断"，
   不是"效果量级的估计"。

---

## 6. 所以什么时候值得拆多 Agent

按本次实验能支撑的范围，只有一条可以直接写下来：

> **如果拆分的唯一动机是"让 Agent 记住更早的东西"，不要拆——把窗口/共享记忆开大就行。**
> 本次实测：窗口够 → 不拆也 1.00；窗口不够 → 拆了也不是因为"分工"赢的。

另外三条（权限隔离、上下文隔离、对抗式校验）在 ADR-W9-002 里给了判据，
但**本次实验没有证据**。诚实的说法是"这三条我们有判据、有实现，但没量化"。
