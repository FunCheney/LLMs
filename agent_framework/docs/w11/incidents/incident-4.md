# INC-4 · `parse_api_keys("=alice")` 静默跳过：某个人突然 401，日志里什么都没有

- **发现时间**：W10 D5（写完 `parse_api_keys` 后的自审，由 INC-3 的同一种坏味道引出）
- **严重度**：P1（一个人被锁在门外，而系统"看起来正常"）
- **影响面**：`API_KEYS` 里任何一条写错的条目

## 1. 现象

`API_KEYS="sk-a=alice,=bob,sk-c=carol"`。第二条缺 key（可能是轮换时删了一半）。

结果：`bob` 从此每次请求都是 401 `AUTH_INVALID`。而**服务端日志里一条相关记录都没有**——
没有 parse 错误、没有 warning、没有"跳过了 1 条"，因为当时的实现是 `continue`。

## 2. 根因

```python
key, _, subject = item.partition("=")
if not key:
    continue          # ← 这一行
```

作者的想法是"空条目跳过"。但 `continue` 把**两类完全不同的情况**合并了：

| 情况 | 正确的处理 |
|---|---|
| 空字符串（`sk-a=alice,,sk-c=carol` 的中间那个） | 跳过，这是用户的排版问题 |
| `=alice`（有 subject 没 key） | **报错**，这是配置写坏了 |

合并之后，"配置写坏了"表现得和"用户多打了个逗号"一模一样：静默。

## 3. 修复

```python
if not key:
    raise ValueError(f"API_KEYS 条目缺少 key：{mask_secret(item)}")
```

两个细节：

1. **用 `mask_secret()` 打错误信息**，不能打原文——错误日志也会被收集、被贴进工单；
2. 空条目（全空白）在进入解析前就被过滤掉了，所以这里抛错不会误伤"多打了个逗号"。

同时把 `sk-x=:admin`（有 key 没 subject）也改成报错——
"没写 subject"会退化成 `key-<hash>`，那不是一个身份，是一个哈希前缀，
审计时无法回答"这是谁"。

## 4. 为什么这条值得单开一篇

它是一条**不会自己暴露**的故障：

| 观察点 | 看到什么 |
|---|---|
| 服务健康检查 | 绿 |
| 错误率 | 上升了一点点（一个人的流量） |
| 日志 | 什么都没有 |
| 受影响用户 | "我昨天还能用" |

发现它的唯一方式是**有人抱怨**。所以修法不能是"下次小心点"，
只能是"把静默分支改成抛错"。

## 5. 回归用例

| 用例 | 断言 |
|---|---|
| `test_auth.py::test_malformed_entry_fails_loudly` | `=alice`（缺 key）与 `sk-x=:admin`（缺 subject）都抛错 |
| `test_auth.py::test_key_is_never_logged` | 错误信息里不出现完整 key |

第二条是配套的：**把"静默"改成"报错"之后，错误的载体变成了日志**，
于是日志本身成了新的泄漏面。

## 6. 教训

1. **`continue` 是这些 bug 的通用形状。** 每写一个 `continue` / `pass` / `return None`，
   都要问一句："被跳过的那条，会不会其实是配置写坏了？"
2. **"用户多打了个逗号"与"配置写坏了"必须分开处理**，哪怕它们的表现都是空值。
   前者是容忍，后者是失败。
3. **修静默要顺手修泄漏。** 报错信息里带原始 key，等于用一个 P0 换一个 P1。
