# INC-2 · 隔离封皮流进了文章标题

- **发现时间**：W10 D1（修完 INC-1 之后，看生成的标题）
- **严重度**：P1（不报错、不告警，只是内容里多了一段 XML）
- **影响面**：所有"用用户输入当标题/首句"的入口

## 1. 现象

`POST /v1/article` 成功返回 200，但标题是：

```
<untrusted source="user">内容营销怎么做</untrusted>：为什么现在做已经晚了一步
```

没有任何错误、没有告警、红队全绿、误报率 0%。**这是 INC-1 修复的副作用**：
为了让检测看到"内层文本"，`unwrap` 拿到的 `inner` 被顺手当成了正文继续往下传。

## 2. 根因

`unwrap()` 返回两个值 `(inner, source)`。调用方只关心"能检测就行"，
把**整个** `inner` 拿去用了——而 `inner` 是"为了匹配规则而剥出来的文本"，
不是"该给下游的文本"。

一句话：**检测用的投影被当成了数据本身**。这类 bug 的特征是"完全不报错"，
因为两段字符串在类型上都是 `str`。

## 3. 修复

`SEOPipeline.run()` 开头显式解封皮，并把"剥出来的正文"与"原始入参"分开：

```python
topic, _wrapped = unwrap(topic, source=SOURCE_USER)
```

同时把这条写进回归用例——因为**红队和误报率都发现不了它**：
- 红队只看"注入拦没拦住"，封皮泄漏不是注入；
- 误报率只看"正常输入放没放行"，它放行了，只是放行得脏。

## 4. 为什么这条比 INC-1 更值得记

INC-1 会 500，用户会骂，两小时就修完。
INC-2 会**静默产出脏数据**，而脏数据的下游是"发布到小红书"。

| 维度 | INC-1（报错） | INC-2（静默） |
|---|---|---|
| 发现方式 | 第一次请求就炸 | 靠人眼看出标题里有尖括号 |
| 自动化能否发现 | 能（任何断言都要过 HTTP 200） | **不能**（除了专门的泄漏断言） |
| 修复后是否留痕 | 是（错误码进日志） | 否 |

## 5. 回归用例

| 用例 | 断言 |
|---|---|
| `test_article_route.py::test_isolation_envelope_does_not_leak_into_the_article` | 成文结果里不出现 `<untrusted` 与 `</untrusted>` |

这条断言写的是**否定式**（"不得出现"），而不是"标题等于某段文本"——
后者会在换一次模板文案之后失效，而前者不会。

## 6. 教训

1. **`unwrap` 的返回值要有明确语义**。"剥出来的内层文本"是检测的输入，
   不是业务数据。两者混用不会报错，只会脏。
2. **静默脏数据比报错更贵。** 报错有日志、有告警、有 error_code；
   脏数据只有人眼。所以每一条"文本会流到下游"的路径，都该有一条否定式断言。
3. **修 A 的副作用要当成新 bug 处理。** INC-1 的修法是对的，
   但它引入的泄漏需要一条独立用例来钉住，而不是"顺手看看没问题"。
