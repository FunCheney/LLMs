# W11 D5 · 资产版本、Feature Flag 与 Kill Switch

> **一句话**：六类资产各自有可计算的版本号、快照 digest 落在 `73c0d2ec`；
> 两个 Feature Flag 默认关闭（= 旧行为）；Kill Switch 实测 **0.5s 生效**（判据 ≤300s）。
> 镜像 tag 回退**未实跑**，如实列在缺口里。

---

## 1. 为什么"回滚代码"不够

系统的行为由六样东西共同决定。只给代码打 tag，等于只能回滚 1/6——
而剩下 5/6 里最容易在下班前被改的，恰好是 prompt 和检索参数。

| 资产 | 版本从哪来 | 本周实测值 | 回滚动作 | 实跑？ |
|---|---|---|---|---|
| 代码 | `GIT_SHA` 环境变量 | `dev`（本地未构建镜像） | 回退镜像 tag（RUNBOOK §10） | ❌ 未实跑 |
| 模型 | `models.yaml` 的 alias → 厂商模型名 | 5 个 alias，如 `qwen3.7-plus → qwen:qwen3.7-plus-2026-05-26` | 改 alias 指向后重启 | ✅ |
| Prompt | 构造 prompt 的模块源码指纹 | `client 9bea11a2` / `answer 32b3017f` / `seo 61ac3bee` / `style f2d2e781` | 回退该模块所在镜像 tag | ⚠️ 见缺口 1 |
| 工具 / Skill | `SkillSpec.version` + 内容指纹 | **缺失**（`missing_kinds=('skill',)`） | 切回上一版 spec 文件 | ❌ W8 的 Skill 未接入快照 |
| RAG 策略 | 检索参数组哈希 | `f9a0f862` | 切回上一组参数并重启 | ✅ |
| 记忆策略 | `MEMORY` 取值 | `off` | 切 env | ✅ |

快照由 `runtime/assets.py::capture()` 生成，整份写进 `evals/history`：

```
digest        73c0d2ec
captured_at   2026-11-13T02:38:10Z
missing_kinds ('skill',)     ← 空的不许静默：少一类就少一条回滚路径
```

### 版本号必须能"自己变"

手填的版本号一定会忘，所以除了 Skill 的 `version` 字段，其余五类全部用**内容指纹**：
改了内容，版本就变。代价是号不可读（`f9a0f862`），所以每个 `AssetVersion` 都带
`source` 说明"这个号怎么算的"、`rollback` 说明"怎么退"。

`skill_drift()` 抓的是另一种失效：**内容改了但 `version` 没改**。
实现时踩过一个坑——最初把判据写成"键变了就报"，结果"改了内容也改了版本号"
这种**正确做法**也会被报出来。一份整天误报的清单，最后没人看：

```python
if previous_version == declared and previous_fingerprint != fingerprint:
    drifted.append(...)   # 只有"版本没跟上内容"才该报
```

### 快照会自己变，这是它的功能

同一个 digest 在一天内从 `6d51c104` 变成 `73c0d2ec`，因为这一轮改了 `client.py`
（加缓存接线）与 `difficulty_router.py`——两个文件都在 `PROMPT_MODULES` 或
代码指纹的覆盖范围内。**这不烦人，这正是"哪一期跑的是哪套东西"能被回答的原因。**

## 2. Feature Flag：默认值必须是旧行为

`runtime/flags.py`。在册两个开关：

| Flag | 控制的路径 | 默认 | 清除期限 |
|---|---|---|---|
| `semantic_cache` | 相似 query 复用结果（省钱） | **关** | 2027-01-31 |
| `difficulty_router` | 简单任务走 cheap（省钱） | **关** | 2027-01-31 |

配置：`FEATURES="semantic_cache=on,difficulty_router=10%"`。

### 三条不妥协的细节

1. **默认值是 `False`，并且有测试逐个断言。** 默认值是新行为的话，回滚就得改代码
   发版——那 Feature Flag 只增加了一层复杂度，没有换来任何可回退性。
   `test_every_flag_defaults_to_the_old_behaviour` 看着像废话，它是唯一能挡住
   "顺手把默认值改成 True"的东西。

2. **拼错的开关名在启动时炸掉。** `semantic_cach=on` 如果被静默忽略，
   结果是"运维以为开了、指标没动、而没有任何东西变红"。启动失败比三天后发现便宜。

3. **灰度按主体稳定分桶**：`sha256(flag:principal) % 10000`。
   `10%` 的含义必须是"同一批人持续走新逻辑"。每请求随机会让同一用户在新旧行为间
   来回跳，任何跨多次请求的 bug 都复现不出来，而用户看到的系统像在抽风。
   匿名流量（无 principal）直接判关——"同一批人"这个前提对它不成立。

### 两个刻意**不**做成 Flag 的东西

写在 `FLAGS` 旁边的注释里，因为"为什么不是 Flag"比"是 Flag"更容易被问：

- **`circuit_breaker`**：已经有 `BREAKER_ENABLED`（W11 D2）。同一行为两个开关，
  必然出现"A 关了它还在跑"，而排查时两个人各看一个开关。类型化布尔保住了。
- **`batched_rewrite`**：把三平台改写合并成一次调用，W8 已实测否决
  （LinkedIn 的段落结构被带进 X，X 文案出现空行，`validate()` 拦下）。
  给一个被否决的方案配开关，等于给"开着但没人敢开"的代码办长期居留。

## 3. Kill Switch 演练（真跑，0.5 秒）

脚本 `evals/scripts/kill_switch_drill.py`。它真的起 uvicorn、真的发 HTTP、
真的改 env 重启，不是"读一下代码说它会生效"。

```
阶段 1 · 开着（FEATURES=semantic_cache=on）
  启动 0.47s；同一 brief 两次：RequestLog 2 条，cache_hit 1 条
阶段 2 · 决定回退 → 生效（计时开始）
  启动 0.47s；同一 brief 两次：RequestLog 2 条，cache_hit 0 条
  → 从决定到生效 0.5s（判据 ≤300s）
  → 期间不可用 ≈ 0.5s
阶段 3 · 回退后系统仍可用
  /v1/draft 正常返回 26 字，model=fixture
结论：Kill Switch 有效，0.5s 生效（预算 300s），回退后仍可应答。
```

判据三项全部落实：

| 判据 | 结果 |
|---|---|
| 触发方式 | `FEATURES` 改值 + 重启（做 env + 重启，够用） |
| **从决定到行为生效 ≤5 分钟** | **0.5s** |
| 回退后 `make eval` 仍绿 | `run_smoke.py` 10/10 PASS（CI 的离线档） |

「期间错过的请求数」的量纲就是不可用时长：**0.5s**。本地回环上重启快，
真实环境还要加容器编排的滚动时间，所以报告里给的是**这个脚本能证明的部分**：
从改 env 到 `/health` 通、到新行为被观测到，全部在 1 秒内。

### 为什么用 mock 厂商演练

一个"要先配 key 才能演练"的回退流程，在出事那天一定演练不了。
`mock` provider 走离线回放，所以这条演练在任何机器上都能跑。

### 一个顺带发现的坑

最初演练想用响应体判断命中（命中则 `input_tokens == 0`），实测**不成立**：
`/v1/draft` 返回的 `input_tokens` 描述的是"这个答案当初花了多少"（它的出处），
不是"这次请求花了多少"。命中与否是**运营口径**，它只存在于 `RequestLog`。
这也正是给 `RequestLog` 加 `cache_hit` 字段的理由——两个口径混在一个数字里，
成本看板会同时错两次。

## 4. 回滚演练：配置回退 ✅ / 镜像 tag 回退 ❌

| 类型 | 动作 | 状态 |
|---|---|---|
| 配置回退（能力开关） | `FEATURES` 改值 + 重启 | ✅ 实跑，0.5s（见 §3） |
| 配置回退（模型指向） | 改 `models.yaml` 的 alias 后重启 | ✅ 机制同 §3（同一条重启路径） |
| 配置回退（检索参数） | 切回上一组 `RETRIEVAL_*` + 重启 | ✅ 快照 digest 会变，可核对 |
| **镜像 tag 回退** | `docker compose` 换 tag 重启 | ❌ **未实跑**（缺口 2） |

镜像回退没实跑的原因不是"麻烦"，是本机没有既有镜像：`ops/Dockerfile` 的构建
需要把仓库外的 `06_rag/rag_mvp` 作为 `additional_contexts` 传进来，
本机没有这套上下文，构建跑不起来。**没有产物就没有"回退到上一版"这件事**，
所以这条如实记为缺口，而不是写"已验证"。

可执行步骤（待有镜像的环境执行）：

```bash
docker tag <repo>:w11 <repo>:w11-prev          # 上线前先打好上一版 tag
docker compose -f ops/docker-compose.prod.yml up -d   # 本次上线
# ── 出事 ──
IMAGE_TAG=w11-prev docker compose -f ops/docker-compose.prod.yml up -d
bash ops/deploy_check.sh                        # 健康检查 + 一次真实请求
```

## 5. 成本三手段单变量 A/B

脚本 `evals/scripts/cost_ab.py`。**token 是估算的**（`字符数/2`，与生产
`usage.estimated=True` 同一口径），价格取自 `models.yaml` 的公开报价，
所以结论是**相对差**，不是账单金额。

### 实验 1 · 语义缓存

| 臂 | 请求 | 上游调用 | 命中 | 成本（USD，估） |
|---|---|---|---|---|
| off | 16 | 16 | 0 | 0.000593 |
| on | 16 | 10 | 6 | 0.000370 |

命中率 37.5%、成本 −37.6%。语料构成说清了才有意义：8 个问题各问两次，
其中 **4 组逐字重复（4/4 命中）**、**4 组改写末尾一个词（2/4 命中）**。
0.92 的阈值不是"什么都能命中"，这是设计意图——把"差不多的问题"当成同一个问题，
是语义缓存唯一会静默给出错答案的地方。

### 实验 2 · 难度分流（结论反直觉，两个基线都报）

| 基线 | 臂 | 成本（估） | cheap 占比 | 简单→强档 | 硬→便宜 |
|---|---|---|---|---|---|
| chat→strong（质量优先） | off | 0.011118 | 0% | 6 | 0 |
| | on | 0.005850 | 50% | **0** | **0** |
| chat→cheap（当前 yaml） | off | 0.000450 | 100% | 0 | 6 |
| | on | 0.005850 | 50% | 0 | **0** |

- 质量优先基线上：成本 **−47.4%**，且 12 条样本零误分流；
- 当前 `models.yaml` 基线上：成本 **×13**（0.00045 → 0.00585）。

**分流不"省钱"，它把钱花在需要的请求上。** 当前 `chat → cheap` 时，
把硬请求升级到强档是**加钱买质量**；只有当基线本来就把所有请求发给强档时，
它才省钱。只报后一半就是挑数字。

### 一个被实验逼出来的设计缺陷

第一版信号表里 `hard_intent` 权重是 1（与"文本长度"同权），阈值 2。
实测 6 条硬样本有 **4 条只拿 1 分**，落回便宜档——一句短而难的
"规划一下灰度方案"被当成简单请求。修法是把 `hard_intent` 提到权重 2：

两个方向的误判代价并不对称。硬请求误走便宜档：省了钱、**可能答错，而答错当天
没人会发现**。简单请求误走强档：多花 20 倍单价，但看得见、可回滚、答案仍是对的。
在没有真实质量数据能标定权重之前，宁可偏向强档。

### 实验 3 · 批处理（串行 vs 并发）

| 臂 | 墙钟 | 调用数 |
|---|---|---|
| 串行 | 0.604s | 3 |
| 并发 | 0.202s | 3 |

加速比 **2.99×**，调用数不变：**批处理省的是延迟，不是钱**。

"合并成一次调用"这条路 W8 已实测否决，本周不重测——重测需要真实上游输出，
离线环境复现不出来，硬造一个"串味文本"再去断言它被拦，是自证。
结论保留在 `growth_agent/pipeline/style.py` 的注释里：三平台各有独立 prompt，
合并会让 LinkedIn 的段落结构污染 X。

## 6. 缺口（宁可少写一条"达标"，不写一条假的）

1. **Prompt 版本是"模块源码指纹"，不是"模板指纹"。** prompt 拼在代码里，
   没有模板文件可哈希。改了 prompt 指纹一定变，所以它能当版本用；但它**不能**
   回答"这次只改了 prompt 还是也改了逻辑"。根治办法是把模板外置成文件，
   接口（`AssetVersion`）不用动。
2. **镜像 tag 回退未实跑**（§4）。缺的是构建产物，不是步骤。
3. **Skill 未接入快照**：`missing_kinds=('skill',)`。W8 的 Skill 在
   `tools_skills_dir` 里按需加载，`capture()` 目前只在显式传 `skills=` 时才有
   这一类。接入点是"启动时把已加载的 spec 传进去"，没做。
4. **语义缓存是进程内缓存**，多副本之间不共享：副本 A 命中不代表 B 命中，
   所以集群的命中率会被稀释，且"重启即清空"。要不要上共享缓存，
   需要先有真实命中率数据（当前只有离线语料的 37.5%）。
5. **难度分流是词面启发式**，没有质量数据标定。误分流风险靠"偏向强档"兜，
   不靠准确率。真正的标定要等在线质量指标（judge 分）积累出来。
6. **Kill Switch 是"env + 重启"**，不是热更新。0.5s 是本地回环的数字，
   容器编排下要加滚动更新时间。配置中心热更新没做。
