### 工具是如何加载并发送给模型进行 function_calling 的
大模型在推理并决定是否调用工具（function calling）之前，必须拿到所有可用的工具的元数据清单（Schema）。

#### 执行路径如下
大模型本身无法直接感知外部世界，它只能通过你传入的 tools 参数来了解“自己有哪些能力可用”。

* 聚合工具清单：你的应用程序（MCP Host / Agent）在发起请求前，会先通过 session.list_tools() 拉取各个 MCP Server 暴露的工具定义，
    再合并你本地自己编写的 Python 函数工具。 
* 格式转换与注入：将这些工具统一转换为大模型 API 要求的 JSON Schema 格式（包含 name、description 和 parameters），连同用户的提问一起发送给大模型。 
* 模型决策与路由：模型阅读所有工具的描述和参数说明，判断是否需要调用工具。如果需要，它会返回具体的工具名称和提取出的参数（模型不会自己运行代码）。 
* 本地/远端执行与回传：你的代码接收到指令后，判断该工具属于本地函数还是某个 MCP Server，分别在本地执行或调用 session.call_tool()，
   最后把执行结果作为新的消息发回给模型，由模型总结出最终回答。

#### 工具数量太多时的工程优化
虽然理论上要把所有工具都发给模型，但当接入多个 MCP Server 导致工具总数达到几十甚至上百个时，全量发送会带来Token 消耗剧增、推理延迟变高以及模型选错工具（注意力分散）的问题。
在实际生产中，通常会采用以下策略来控制每次发给模型的工具数量：

##### 意图路由（Intent Routing）
先用一个轻量级小模型或分类器判断用户意图（例如“查数据库”还是“发邮件”），只把对应分类下的工具清单传给主模型。


##### 工具检索（Tool RAG）
将所有工具的名称和描述存入向量数据库。每次收到用户提问时，先检索出语义最相关的 Top-K（如前 5～10 个）工具，仅将这批候选工具发给大模型。

这是目前应用最广的方法，核心思想是把工具当作“文档”来检索，借鉴了 RAG（检索增强生成）的思路。其流程是：

1. 离线索引：在会话开始前，将所有工具的名称、描述、参数说明等元数据，通过嵌入模型（Embedding Model）转化为向量，存入向量数据库。

2. 在线检索：当用户提出一个请求时，系统将用户 query 同样向量化，然后在工具库中进行语义相似度搜索，召回最相关的 Top-K 个候选工具。

3. 注入上下文：将这 K 个候选工具的完整定义，动态注入到当前对话的上下文中，供模型进行最终的 Function Calling 选择。

业界常将语义搜索与 BM25 关键词匹配结合，形成混合检索（Hybrid Search），以提升对专有名词、缩写等精确匹配场景的召回率。
这种方法可以将候选工具从成千上万个大幅缩减到个位数或十几个，在控制上下文长度的同时，保持较高的选择准确率。

##### 按需动态加载（Meta-Tool 模式）

只给模型提供一个类似 search_tools 的元工具。模型发现当前没有合适工具时，先调用该工具搜索可用能力，应用层再动态把搜到的新工具挂载到下一轮对话中。

1. 仅暴露“搜索工具”：在请求开始时，不发送所有业务工具，而是只发送一个名为 search_tools（或 tool_search）的元工具（Meta-Tool），外加少量核心基础工具。

2. 模型发起检索：当模型判断需要外部能力时，它会首先调用 search_tools，并附上一个描述需求的查询语句（如“github”、“database”）。

3. 后端返回并注入：你的后端接收到这个搜索请求后，执行实际的检索（可以是语义搜索、关键词匹配或正则匹配），找到匹配的工具，然后将这些工具的完整定义通过一条特殊的系统消息动态注入到对话中。

4. 模型执行调用：模型看到新注入的工具定义后，便可以直接调用它们来完成任务。

你甚至可以通过设置 tool_choice: "required"，强制模型在第一轮必须调用搜索工具，确保它在回答前先进行工具发现。


#### 基于会话上下文的动态注册与过滤
种方法更侧重于会话生命周期和运行时状态的管理：

1. 会话级工具注册：工具不与全局绑定，而是与具体的会话（Session）关联。系统可以维护一个 sessionTools 的映射，记录每个会话当前已激活的工具集合。

2. 按需动态加载：一个工具只有在被检索命中或被模型显式请求后，才会被“加载”到当前会话中，并在后续轮次中持续可用。

3. 运行时过滤：可以根据运行模式、用户权限或策略，在工具被提供给模型之前进行过滤。例如，某些敏感工具（如“删除数据库”）可以通过配置规则
  （如 isEnabled() 返回 false）对当前会话完全隐藏，模型根本看不到它，从而避免误调用。


### 在模型进行 function calling 之后，如何完成工具的调用
在工程实现中，大模型的返回结果通常只包含一个抽象的工具名称（name）和参数（arguments），它本身并不关心这个工具是在本地运行还是在远程服务器上。

区分并路由这些调用的核心逻辑，是在你的应用程序（MCP Host / Agent 层）建立一个工具注册路由表（Tool Registry / Router）。

具体的实现机制主要分为统一注册表映射和命名空间隔离两个关键步骤：

#### 1. 核心机制：建立“工具路由表”（Tool Registry）
在将工具列表发给大模型之前，你的代码就已经从不同来源收集了工具。此时只需在内存中维护一个字典（dict），将工具名称映射到对应的执行器（Executor）或 MCP 会话（Session）。

路由分发流程

1. 初始化注册：
	* 扫描本地函数，记录 {"local_func_name": {"type": "local", "handler": func_obj}}。
	* 遍历所有已连接的远程 ClientSession，调用 list_tools()，记录 {"mcp_tool_name": {"type": "mcp", "session": session_obj}}。
2. 合并发给模型：将两者的 Schema 合并为一个统一的 tools 列表，发送给大模型。
3. 接收并查表分发：当模型返回 tool_call（包含 name 和 arguments）时，直接用 name 去路由表中查表，根据 type 决定走本地函数执行还是通过对应的 session.call_tool() 发起远程调用。

#### 2. 进阶实践：如何防止重名冲突（命名空间前缀）

如果你接入了多个远程 MCP Server（例如同时接了 GitHub MCP 和 GitLab MCP），或者本地函数恰好和某个 MCP 工具都叫 search_issues，直接存字典会发生覆盖冲突。
工程上最标准的做法是在注册时动态加上命名空间前缀：
* 注册改名：
	* 本地工具保持原名或加 local__ 前缀（如 local__calculate_tax）。
	* 远程 MCP 工具在拼装发给模型的 Schema 时，加上服务标识前缀（如 github__search_issues、db__query_sql）。
* 执行还原：
	* 当模型返回调用 github__search_issues 时，你的路由代码解析出前缀 github，找到对应的 GitHub ClientSession。
	* 剥离前缀还原出原始工具名 search_issues，再传给 session.call_tool("search_issues", arguments)。


#### 3. 主流 Agent 框架的自动处理方式
* LangChain / LangGraph：使用 langchain-mcp-adapters 将远程 MCP 工具转换为标准的 LangChain StructuredTool 对象，
    与本地 @tool 装饰器定义的函数放进同一个列表即可，ToolNode 会自动分发执行。
* OpenAI Agents SDK：支持直接向 Agent(tools=[local_func], mcp_servers=[mcp_server]) 同时传入本地函数和 MCP 服务实例，
    SDK 内部会自动完成命名空间隔离和执行路由。
