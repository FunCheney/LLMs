# 案例 1 · 检索层：BM25 把 `？` 当 token，问句类查询被"问题列表段"劫持

- 日期：2026-W45 · 归因层：**检索层**（`docs/w4/root-cause-playbook.md` 的 `retrieval_miss`）
- 涉及文件：`06_rag/rag_mvp/src/rag_mvp/embedding/tokenizer.py`、`embedding/bm25.py`、`pre_query/`
- 数据：`data/eval/golden_queries.yaml`（28 正例 / 2 负例）、425 chunk、`bge-m3` 1024 维

## 1. 现象

六档检索评测跑完之后，两件事同时成立，而且互相矛盾：

| 配置 | R@1 | R@10 | MRR |
|---|---|---|---|
| dense | .7857 | 1.0000 | .8628 |
| sparse | **.2500** | .7143 | .4227 |
| hybrid | .5714 | .9643 | .7063 |

- sparse 的 R@1 只有 .25 —— 四道题里三道排错，这不像是"BM25 不适合中文"能解释的量级；
- hybrid 的 R@10（.9643）比 sparse（.7143）高很多，说明融合**确实捞回了** dense 漏掉的
  东西，但它的 R@1 却比 dense 低 21 个百分点 —— 融合在"捞回"的同时把对的挤下去了。

单看这两行，最自然的结论是"混合检索这个方向不行"。**这个结论是错的**，
至少不完整。

## 2. 定位

拿一条最能说明问题的用例：`golden-018`「如何配置 MCP 服务器？」。
gold chunk 是 `claude-code-0001-p157-p157-c343`（第 19.7 节「配置 MCP 服务器」，
正文是一段 JSON 配置示例）。

| 检索档 | gold chunk 的名次 |
|---|---|
| dense | **1** |
| sparse | 未进 top10 |
| hybrid | 未进 top10 |

sparse 的 top5 是：`p069-c149` / `p159-c347` / `p085-c177` / `p158-c346` / `p153-c335`。
除了 `p069-c149`，其余全是第 19 章 MCP 的**邻居页**——它召回到了正确的章节，
但选中了错的那一段。

于是把分词结果打出来：

```python
tokenize("如何配置 MCP 服务器？")
# ['如何', '配置', 'mcp', '服务器', '？']   ← 问号是一个 token
```

再看这几个 chunk 里，查询 token 的出现次数：

| chunk | 内容形态 | 服务器 | mcp | 如何 | ？ |
|---|---|---|---|---|---|
| `p069-c149`（被排到第 1） | "六个根本问题"的列表 | 0 | 0 | **7** | **12** |
| `p085-c177` | MCP 工具表 | 3 | 5 | 0 | 0 |
| `p153-c335` | MCP 客户端源码 | 6 | 5 | 0 | 0 |
| `p159-c347` | MCP 设计哲学（散文） | 5 | 6 | 0 | 0 |
| **`p157-c343`（gold）** | **JSON 配置块** | **1** | **2** | 0 | 0 |

## 3. 根因

`rag_mvp/embedding/tokenizer.py` 只过滤空 token：

```python
return [token.strip().lower() for token in jieba.lcut(text) if token.strip()]
```

于是标点、符号全部成为有效 token。两个后果叠加：

1. **`？` 成了检索信号。** 「如何配置 MCP 服务器？」里的 `？` 让**任何**含大量问号的
   段落（FAQ、问题清单、"需要回答几个问题"）对该查询天然高分。`p069-c149` 里
   `？` 出现 12 次、`如何` 7 次——它是一段"设计工具系统要回答哪六个问题"的列表，
   和"怎么配置 MCP 服务"毫无关系，却拿到了 sparse 的第 1 名。
2. **代码块型 chunk 在词袋模型里天然吃亏。** gold chunk 是 JSON 配置，`服务器`/`mcp`
   各只出现 1–2 次（配置示例里不会反复复述"服务器"），而散文型邻居页各出现 5–6 次。
   BM25 的 tf 项直接把它压到后面。**这不是分词的锅，是 BM25 的固有偏好**——但它
   解释了为什么"召回到了正确章节、选中了错误段落"。

换句话说：`retrieval_miss` 的真实根因不是"BM25 不适合中文"，也不是"RRF 参数不对"，
而是**输入口径（分词）把一个无关信号（标点密度）当成了相关性**。

## 4. 改动与量化

只换分词器，其他一切不变（同语料、同 gold、同 `BM25Okapi`、同 `RRF`）：

| 分词口径 | sparse R@1 | R@10 | MRR | hybrid R@1 | R@10 | MRR |
|---|---|---|---|---|---|---|
| v1 现状 | .2500 | .7143 | .4227 | .5714 | .9286 | .6921 |
| v2 去纯标点 token | **.5357** | .8571 | .6329 | .5714 | .9643 | .7074 |
| v3 v2 + 疑问/虚词停用表 | .5357 | .8571 | **.6433** | .6429 | .9643 | **.7427** |

- **sparse R@1 从 .2500 到 .5357（+114%）**，MRR +47%——一个三行的过滤条件换来的；
- hybrid 也跟着涨（R@1 .5714 → .6429），但**仍然低于 dense 单路（.7857）**。

第二件事同样重要：**修好分词器并不会让混合检索翻盘**。因为 RRF 是等权名次融合，
正确答案"在 dense 排 1、在 sparse 排 30"时拿 `1/61 + 1/90 = 0.0275`，而一个
"两路都排第 5"的邻居页拿 `2×1/65 = 0.0308`——**两路都中庸胜过一路极好**。
所以这是两个独立的缺陷：分词器坏了（可修、已量化修复收益），
和 RRF 在"一强一弱"场景下会做平均（是算法性质，不是 bug）。

## 5. 结论与后续

1. **`retrieval_mode` 默认档改为 `dense`**（`Settings.retrieval_mode`），
   `hybrid` 保留但默认关；依据见 `docs/w5/adr-w5-retrieval-stack.md` D6。
2. **分词器缺陷记为 rag_mvp 的待修项**：`tokenize()` 增加"只保留含字母/数字/汉字
   的 token"。修完必须重跑上表四行——混合检索才重新获得竞争力。
   （本案例的 v2/v3 是实验口径，尚未落进 `tokenizer.py`：改它会改变 `bm25.pkl`
   的数值分布，需要同时重建索引并把新旧召回结果对齐，属于独立的一次改动。）
3. **归因纪律**：指标整体偏低时，先看"输入口径"（分词、归一化、字段映射），
   再看"算法选择"。这次如果直接下"BM25 不适合中文"的结论，会去换检索器、
   换 embedding，而真正坏掉的是三行代码。
