## 0. 结论先行

| 组件 | 决策 | 依据（一句话） |
|---|---|---|
| 混合检索（BM25 + RRF） | **默认关** | R@1 .5714 vs dense .7857，连修好分词器后仍只有 .6429 |
| 精排（bge-reranker） | **默认关** | R@1 −7.1pp、MRR −4.8pp，1 题变好 / 6 题变坏，p95 从 160ms 涨到 5.4s |
| 查询改写（multi-query） | **默认关** | 两次运行都不如不改，p95 15.2s（+94 倍），每天 1000 次检索 ≈ 3.55 元 |
| 默认档 | **dense 单路** | 唯一在 R@1 / MRR 上都没有劣化的配置 |
| 验收指标 | **改用 R@1 / MRR 主指标** | dense 的 R@10 已经 1.000，检查点"提升 ≥10%"在数学上不可能达成 |

**这一周的结论大部分是负的**：加组件没有让检索变好，反而是把已经正确的 top-1 打散。
这不是"没做完"，是"做了、量化了、然后默认关掉（开关保留）"——任务书 D5 第 3 条要求的正是后者。

## 1. 口径（先说清楚，否则数字无法比较）

生产链路（`Settings` 默认 + 评测覆盖）：

```
query ──[改写？]──> 召回 ×recall_multiplier(3) ──[ACL]──> [精排：只重排前 rerank_candidates(20) 条]
      ──[治理]──> 截断 top_k(10)
```

评测时 **`top_k=10`**（不是生产默认的 8）：`Recall@10 / nDCG@10` 需要 10 条才有意义。
其余参数一律走 `Settings`，脚本只改 `Settings` 字段，装配仍走 `growth_agent.rag.build_pipeline`
——评测自己拼一套参数，报告上的数字就不再是生产数字。

指标定义（与 rag_mvp `golden_runner` 同算法，**交叉验证见 §5**）：

- `Recall@K`：top-K 里至少命中一个 gold chunk 的题目**占比**（分母 = 28 条正例）；
- `MRR`：首个 gold 命中名次的倒数均值，未命中记 0（不剔除样本）；
- `nDCG@10`：二值相关度，`DCG=Σ 1/log2(rank+1)`，`IDCG` 假设所有 gold 排最前；
- 负例（2 条，期望拒答）**不进检索指标**，只计数——"拒答正确"和"召回失败"是两件事。

## 3. 精排：为什么关（含逐题证据）

两套候选池口径，同一批数据：

| 口径 | 候选池 | R@1 | R@10 | MRR | p95 |
|---|---|---|---|---|---|
| dense 单路 | 30 条召回 | **.7857** | **1.0000** | **.8628** | 175ms |
| 精排（rag_mvp 历史口径） | 100 条全局重排 | .7143 | .9643 | .8146 | **20.9s** |
| 精排（框架生产口径） | 20 条 | .7143 | .9643 | .8146 | 5.4s |

**两行精排的数字一模一样（四位小数全同、连 miss 的题都一样）**。这一点否掉了一个
常见猜测——"负收益是因为候选池 100 条太大、把 top10 打乱了"。池子缩到 20 条，
损伤一点没少：问题在 cross-encoder 的判断，不在池子大小。

逐题比较首个 gold 的名次（dense → 20 条精排）：

| 变化 | 题数 | 明细 |
|---|---|---|
| 变好 | **1** | `golden-013`：2 → 1 |
| 变差 | **6** | `golden-002` / `004` / `008`：1 → 2；`golden-014`：2 → 3；`golden-025`：5 → 7；`golden-022`：8 → 出局 |
| 不变 | 21 | |

`golden-022`（"CLAUDE.md 和 Memory 该如何选择？"）是最干净的样本：dense 把
`p115-p115-c249`（正文里正好对比两者）排在第 8；精排后它掉出 top10，而精排把同一页
的邻居 `c250`、`c229` 顶上来。**精排偏好"主题邻近的段落"，而这类对比题要的是
"恰好回答这个问题的那一段"**——cross-encoder 的"语义贴合度"与"这段是不是答案"
在对比/操作型问题上不是一回事。

延迟侧更直接：20 条候选在本机 CPU 上 p95 **5.4s**，100 条 **20.9s**。
生产预算 800ms，开着它等于每次都在 `budget_exhausted` 降级——降级路径天天跑，
等于没开，还白烧 CPU。

**能力保留，默认关**（`retrieval_rerank=False`）。换语料、换精排模型（例如拿本语料
做 hard negative 微调）都可能翻盘，删掉代码等于删掉实验入口；而默认关是因为开着的
代价是确定的（+5s p95、−7pp R@1），收益是零。要开必须三个值一起给：

```bash
RETRIEVAL_RERANK=true
RETRIEVAL_BUDGET_MS=8500     # ≥ rerank_timeout(8000) + 500ms 召回余量
RETRIEVAL_DEVICE=cpu         # macOS 必设
```

少一个都会静默降级，所以启动时 `rerank_preflight()` 会把这些不自洽直接报出来。
操作步骤见 `ops/RUNBOOK.md` §5「开精排：三个值缺一不可」。

## 4. 改写：为什么关（成本换召回，换不到）

| 项 | 数值 |
|---|---|
| R@1 | .7857 / .7143（两次） vs dense .7857 → **不变或更差** |
| R@3 | .8571 / .8571 vs .9286 → **更差** |
| MRR | .8482 / .8089 vs .8628 → **更差** |
| 延迟 p50（改写本身） | **8.7s** |
| 延迟 p95（整条检索） | 15.2s（dense 是 160ms，**+94 倍**） |
| 超时降级 | 3/28、4/28（`rewrite_timeout_ms=15000` 之下仍超时） |
| 成本 | 25 次成功调用 4150 输入 + 10060 输出 token = **0.0888 元**，即 **0.0036 元/次** |

**为什么改写质量不升反降**（机制，不是猜测）：multi-query 把 N 条查询各自召回后用
RRF 融合，和 §6 的混合检索是同一个机制——RRF 会把"某条改写召回得更好"和
"某条改写召回得偏"平均掉。原查询本来就是最准的那条，把它的第 1 名和三条改写
的第 5 名平均，结果就是第 2、第 3 名。

**成本侧有个必须记下来的事实**：我们请求 `max_tokens=160`，实际输出均值
**402 token/次**——该模型把思考 token 计入 output，`max_tokens` 并不约束总输出量。
所以成本预算必须按**实测 token** 算，不能按 `max_tokens` 估；这也是它 8.7s 的原因。

## 5. 交叉验证：框架口径能否复现 rag_mvp 的历史数字

用框架 pipeline 跑 rag_mvp 的口径（`--preset ragmvp`：top_k=10 / 超取 ×10 / 全局重排 100 条）：

| 配置 | 框架复现 | rag_mvp 存档 | 差异 |
|---|---|---|---|
| dense | .7857 / .9286 / .9643 / 1.0000 / .8628 / .7416 | .7857 / .9286 / .9643 / 1.0000 / .8628 / .7416 | **0** |
| dense+rerank | .7143 / .9286 / .9286 / .9643 / .8146 / .7232 | .7143 / .9286 / .9286 / .9643 / .8146 / .7232 | **0** |

四位小数全对。这一步不是装饰：它同时证明了三件事——指标公式同算法、
`RetrievalPipeline` 的两条路径（单路召回 / 加精排）语义与 rag_mvp 一致、
报告里的"负收益"不是口径差异造出来的。

## 6. 附带发现：hybrid 负收益背后有两个缺陷，不是一个

写 ADR 时我原本把 hybrid 变差归因为"中文分词差"。查证后发现这句话不准确，
真实情况是两个独立问题：

**① 分词器把标点当 token（真 bug，已量化）。** `tokenize("如何配置 MCP 服务器？")`
→ `['如何','配置','mcp','服务器','？']`。于是"满是问号的段落"对任何疑问句天然高分：
`golden-018` 的 sparse top1 是 `p069-c149`（一段"六个根本问题"列表，`？`×12、`如何`×7），
而 gold `p157-c343`（JSON 配置块）里 `服务器`×1、`mcp`×2。

同语料只换分词器：

| 分词口径 | sparse R@1 | MRR | hybrid R@1 | MRR |
|---|---|---|---|---|
| 现状 | .2500 | .4227 | .5714 | .6921 |
| 去纯标点 token | **.5357** | .6329 | .5714 | .7074 |
| 再去疑问/虚词停用 | .5357 | **.6433** | .6429 | **.7427** |

**② 修好分词器，hybrid 依然不如 dense**（.6429 vs .7857）。因为 RRF 是等权名次融合：
正确答案"dense 排 1、sparse 排 30"得 `1/61 + 1/90 = 0.0275`，而一个"两路都排第 5"的
邻居页得 `2/65 = 0.0308`——**两路都中庸，赢过一路极好**。这是算法性质，不是 bug。

两件事的处理不同：① 记为 rag_mvp 的待修项（`tokenizer.py` 加一行过滤，修完要重建
`bm25.pkl` 并重跑本报告全部四行）；② 作为 ADR 的一条决策（关掉 hybrid）。
详细过程见 `docs/w5/case-1-retrieval-punctuation-token.md`。

## 7. 诚实边界

1. **28 条正例**。R@10 的 1 条差异（.9643 vs 1.0000）不显著；R@1 差 6 条、
   MRR 差 4.8pp 是系统性的（逐题表可查）。
2. **单机、CPU、无并发**。p95 是串行 28 次的中位数口径，不含并发排队；
   换 GPU 后精排延迟会好一个量级——但**质量结论不变**（质量问题与算力无关）。
3. **改写延迟含模型自身 8.7s**。这是 `qwen3.7-plus` 在 402 输出 token 下的表现，
   换更快的 cheap 模型可以压到 1–2s；但那仍比 160ms 高一个量级，
   **没有质量收益的前提下，快慢都不该开**。
4. **macOS + MPS 不能开精排**：cross-encoder 跑在 pipeline 的工作线程里，
   torch 2.14 的 MPS 后端会 `A command encoder is already encoding` 断言失败，
   进程直接死（不是异常，降级不了）。评测必须 `--device cpu`，已写进 Settings 注释。
5. **`rerank_timeout_ms` 默认 3000ms 在本机 CPU 上必然超时**（20 条约 3.2–5.4s）。
   第一轮"精排档"就是这样 28/28 全降级、指标等于 dense——脚本的 `deg` 列与
   退出码 1 把这个真相摆出来了。任何"精排没用"的结论必须先在 `deg=0` 下取得。

## 9. 对检查点的修订建议

原检查点：**"Recall@K / MRR 量化提升 ≥ 10%"**。

dense 的 R@10 已经是 **1.0000**，没有 10% 的空间。建议改为：

> 在 R@10 触顶的前提下，用 **R@1 / MRR** 作主指标；混合与精排若为负收益，
> 如实记录并默认关闭。

这不是降标准：以 sparse（.2500 / .4122）为 baseline，dense 的 R@1 提升 **+214%**、
MRR **+109%**，都远超 10%——只是不该继续用已经饱和的 R@10 去衡量。
