# W7 对照实验：上下文压缩与长期记忆值不值

> 两个实验回答两个不同的问题：
> **实验一**：把"全量历史"换成"预算裁剪 + 滚动摘要"，到底省多少、有没有代价？
> **实验二**：加了长期记忆，效果涨多少、成本涨多少——能不能说服人保留它？
>
> 实跑：2026-11-10，`qwen3.7-plus`（路由 `cheap` 档），pgvector `localhost:5433`。
> 原始数据：`evals/history/2026-W50-ab-run.json`。复算：`context_cost_ab.py --replay <文件>`。

---

## 0. 怎么读这两张表

三个数字口径不同，混着看会得出错误结论：

| 指标 | 来源 | 说明 |
|---|---|---|
| `payload_tokens` | 粗估（1.6 字符/token） | 我们自己的预算口径，用来判"会不会撞预算窗口" |
| `input_tokens` | 厂商 `usage`（计费口径） | 表里的主指标；与账单一致 |
| `cost` | `input_tokens × 单价 + output_tokens × 单价` | 单价取自 `models.yaml`，不写死 |

**所有调用都钉住 `thinking=False`**。原因见 §4：不钉住，输出侧的推理 token 会把
输入侧的差异完全盖掉。

## 1. 实验一：压缩有没有用（20 轮，三个 arm）

同一条 20 轮品牌策划对话，同一份"标准答案历史"（由 naive arm 产生后复用），
只改 payload 的构造方式：

| arm | 做法 |
|---|---|
| `naive` | 全量历史直接拼，不裁不压（W6 之前的做法） |
| `budget` | 同一份历史走 `allocate`，history 槽位 2000 token，低分（最旧）先裁 |
| `summary` | 先滚动摘要（阈值 1500 token / 保留最近 6 条），再走同一套预算 |

### 1.1 汇总

| arm | 平均 input tokens | 末轮 input | p95 input | 20 轮会话成本（元） | 摘要成本（元） | **净成本（元）** | 被裁历史条数 |
|---|---|---|---|---|---|---|---|
| `naive` | 1451 | 2758 | 2596 | 0.0661 | 0 | **0.0661** | 0 |
| `budget` | 1434 | 2486 | 2487 | 0.0654 | 0 | **0.0654** | 4 |
| `summary` | **999** | **1630** | **1632** | 0.0480 | 0.0083 | **0.0563** | 0 |

- 平均 input tokens：`summary` 比 `naive` **-31.1%**（999 / 1451）
- p95 input tokens：**-37.2%**（1632 / 2596）
- 净成本（把摘要自己花的钱算进去）：**-14.9%**（0.0563 / 0.0661）
- 输出长度几乎不变（平均 50 / 51 / 50 token）→ 质量侧的"变短"没有发生，
  省下来的是真的冗余

### 1.2 逐轮曲线（input tokens）

| 轮 | naive | budget | summary |
|---|---|---|---|
| 1 | 124 | 124 | 124 |
| 5 | 696 | 696 | 694 |
| 10 | 1401 | 1401 | 1399 |
| 12 | 1670 | 1670 | 1668 |
| **13** | 1807 | 1807 | **679** ← 第一次压缩生效 |
| 15 | 2076 | 2076 | 948 |
| 18 | 2468 | 2468 | 1340 |
| 19 | 2588 | **2507** ← 预算开始裁 | 1460 |
| 20 | 2758 | 2486 | 1630 |

三件事一眼能看出来：

1. **naive 线性增长**，斜率约 **139 token/轮**（`(2758-124)/19`）。按这条线外推，
   `window=8000` 的爆窗点在第 **57 轮**左右——20 轮根本撞不穿，所以"20 轮不爆"
   是个弱结论，真正的结论是"增长有斜率就能算出什么时候爆"。
2. **budget 单独几乎没用**：2000 token 的历史槽位在 20 轮内基本够用，直到第 19 轮
   才开始裁（累计 4 条）。这说明"裁剪"是**兜底**，不是"优化"——它防爆窗，
   不降成本。
3. **summary 是锯齿**：涨到阈值就压一次，回落后重新涨。均值低、尾部低，
   而且被压掉的内容仍在摘要里（第 1 轮的结论能在摘要中查到）。

### 1.3 结论

- **压缩在这个长度上是划算的**：净省 14.9%，且 p95 明显更低（尾部才是延迟和成本的
  痛点）。
- **但省的不是"钱的大头"**：20 轮会话总成本 0.066 元，摘要自己要花 0.0083 元（12.5%）。
  会话越短，压缩越不划算——**拐点在 12 轮附近**（第 12 轮时摘要成本 ≈ 已省下的输入成本）。
- **真正的收益是"可预测"**：naive 的成本随轮次线性上涨、开口无上限；summary 稳定在
  一个平台。做容量规划时，"每条会话最多多少钱"比"平均省 15%"有用得多。

## 2. 实验二：记忆值不值得存在（off vs governed）

同一批跨会话任务，`MEMORY=off`（不注入记忆）与 `MEMORY=governed`（召回 + 注入 `memory`
槽位）各跑一遍。会话 A 先教三条偏好，会话 B（新 session）再提问。

写入结果（会话 A，三轮）：

| 轮 | 内容 | 写入 |
|---|---|---|
| 1 | "记住：品牌调性要专业克制，不要喊口号" | `brand_tone`（新写入） |
| 2 | "记住：标题禁止使用「最」「第一」「绝对」" | `forbidden_words`（新写入） |
| 3 | "以后写文案都用短句，不要用感叹号" | **不写入**（写作手法不是调性，见 §3.2） |

### 2.1 汇总

| arm | 通过 | 通过率 | 平均 input tokens | 成本（元） | 记忆命中 |
|---|---|---|---|---|---|
| `off` | 3/4 | 0.75 | 63 | 0.00160 | — |
| `governed` | **4/4** | **1.00** | 119 | 0.00195 | 4/4 |

- 增量：通过 **+1**，input tokens **+89.2%**，成本 **+22.0%**
- 唯一变好的是"跨会话回忆"这一项（`tone_recall`）：
  - `off`："请提供您的品牌名称或相关资料…"（答不出，因为这一轮没有任何记忆）
  - `governed`："专业克制。"（四个字，正是会话 A 里教过的）

### 2.2 逐任务

| 任务 | 期望 | off | governed | 说明 |
|---|---|---|---|---|
| 写 3 个标题 | 不含绝对化词 | ✅ | ✅ | 模型本来就少用绝对化词，这条**没有区分度** |
| 品牌调性是什么 | 说出专业/克制 | ❌ | ✅ | **唯一有区分度的任务** |
| "最好用"能用吗 | 明确否定 | ✅ | ✅ | 常识题，不需要记忆 |
| 写一句卖点文案 | 不含绝对化词 | ✅ | ✅ | 同第一行 |

### 2.3 结论

- **记忆的价值集中在"用户私有信息"上**，不在"通用常识"上。四个任务里只有一个真正
  需要记忆，其余三个靠模型常识就能过——这也说明**设计评测任务时，"能靠常识答对"的
  题是噪声**，它们只会稀释效果。
- **成本涨幅要带分母读**：input tokens +89.2% 是因为基线只有 63 token；放在真实
  RAG payload（3–4K token）里，多 56 token 约等于 **+1.5%**。同一个数字在不同分母下
  差 60 倍，报告里必须写清楚分母。
- **记忆是"可关的能力"，这一点比效果更重要**：`MEMORY=off` 时链路完全走 W6 行为，
  一条 SQL 都不多跑。能力能被关掉，才谈得上"要不要留"。

## 3. 过程中被数据推翻的三个想当然

### 3.1 "压缩是免费的" —— 错

第一版实验里 `summary` arm 的成本明显更低，看起来压缩稳赚。真相是
`CompressResult.input_tokens` 从没被填过：字段存在、恒为 0、没人发现。

补上 `SummarizerUsage`（摘要器与 `WorkingMemory` 共用同一个累计器）后，20 轮的
净收益从"看起来 -27%"变成"实际 -14.9%"。**任何一个优化，如果它的开销不进报表，
报表就会推荐它。**

### 3.2 "提取器写什么就记什么" —— 错

第一版跑了三轮，`brand_tone` 被第三轮的"以后用短句"顶替掉了——第三个偏好是**写作
手法**，不是品牌调性，但提取器把它归到了 `brand_tone`，而"同 key 顶替"是设计好的
行为，于是真调性被一条错的记忆删了。

修法不是加"冲突检测"（按 key 顶替本来就是对的），而是把 **key 的边界写进提取提示词**：
`brand_tone` 只收"整体语气/人设"，写作手法/标点/格式不算。改完后第三轮正确地
不产生候选。

这条说明：**记忆的错误大多不是"存错了"，而是"归类错了"**——归类错会让顶替机制
替你把对的删掉，而删除是不可见的（旧值只剩一行 `superseded_by`）。

### 3.3 "token 数就是字数" —— 差 60 倍

同一条 26 字的答案，Qwen 默认思考模式下 `output_tokens=876`，`thinking=False` 时
`output_tokens=14`。不钉这个开关，20 轮实验的输出侧成本会从 0.003 元涨到 0.05 元级别，
输入侧的 30% 差异直接被淹没，结论会变成"压缩没用"。

**实验的第一件事是固定测量条件，不是收集数据。**

## 4. 局限（写清楚，免得被当成结论用）

1. **单次跑、单模型**：温度 0.2 仍有采样波动；换模型（尤其换 tokenizer）数字会变。
   结论方向（压缩降 token、记忆提私有信息召回）比具体百分比可信。
2. **20 轮是短会话**：压缩的拐点在 12 轮附近，40 轮以上优势会更明显；这里没跑到。
3. **没跑 live judge**：质量侧只有"输出长度不变 + 规则判定通过率"两个代理指标，
   没有 judge 分数。真正的质量结论要等 W8 补 live judge。
4. **实验二的样本量小**：4 个任务里有 3 个没有区分度，等效样本量是 1。所以结论只能
   说"记忆让跨会话召回从不可能变成可能"，不能说"提升了 25% 通过率"。
5. **记忆用词面哈希 embedder**（本机无 torch）：召回偏保守，真 bge-m3 只会更好。
   召回"没召回到"的情况在这份数据里没有出现，所以这条局限没有实际影响，但要记住。

## 5. 可复现

```bash
# 全量（实验一 + 实验二，本机实测约 5 分钟，需要密钥与 pgvector）
PGVECTOR_DSN=postgresql://rag:rag@localhost:5433/rag \
  .venv/bin/python evals/scripts/context_cost_ab.py \
  --json evals/history/2026-W50-ab-run.json

# 只跑实验一 / 只跑某个 arm
.venv/bin/python evals/scripts/context_cost_ab.py --only exp1 --rounds 20
.venv/bin/python evals/scripts/context_cost_ab.py --only exp1 --arms summary

# 复算（不调 LLM）
.venv/bin/python evals/scripts/context_cost_ab.py --replay evals/history/2026-W50-ab-run.json

# 20 轮预算演示（零密钥，演示档 window=2000 把爆窗点压进 20 轮）
.venv/bin/python scripts/demo_long_session.py
```
