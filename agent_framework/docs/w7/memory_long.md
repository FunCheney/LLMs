## 长期记忆如何实现


### 长期记忆管理哪些内容
支持三种类型，但采用不同的更新策略。

| 类型 | 保存内容 | 更新方式 |
|---|---|---|
| 事实与偏好 | 用户偏好、项目配置、持续约束、决策 | 新增、修订、替代、标记冲突 |
| 经历与案例 | 场景、行动、结果、失败原因、证据 | 追加记录，可以生成概览 |
| 方法与流程 | 适用条件、操作步骤、验证方式 | 候选方法经过验证后发布新版本 |

例如：
```text
事实：
订单项目使用 PostgreSQL。

经历：
某次并发测试发现“先查询再插入”无法阻止重复订单。

方法：
当请求有稳定业务标识、数据库支持唯一约束时，
可采用唯一约束处理该类重复写入，并执行并发验证。
```

事实适合维护当前值，经历适合追加，方法需要验证。 不会用同一种“覆盖旧文本”操作处理三者。

###  核心存储：保留历史，再维护当前有效版本

核心存储：保留历史，再维护当前有效版本

| 存储 | 职责 |
|---|---|
| `sources` | 保存或引用原始消息、工具结果、文档片段 |
| `memory_items` | 记忆身份、所属范围、类型、当前版本 |
| `memory_revisions` | 每个版本的内容、状态、时间和适用条件 |
| `memory_evidence` | 记忆版本与来源之间的关联 |
| `memory_derivations` | 总结、方法依赖了哪些记忆版本 |
| `outbox` | 等待执行的索引、失效和整理任务 |

一条记忆可以表示为：

```json
{
  "memory_id": "mem_101",
  "revision": 2,
  "scope": {
    "tenant_id": "org_a",
    "project_id": "orders"
  },
  "kind": "semantic",
  "subject": "orders_project",
  "predicate": "database",
  "content": "订单项目使用 MySQL",
  "status": "active",
  "evidence_type": "tool_observation",
  "evidence_refs": ["source_245"],
  "observed_at": "2026-10-29T10:00:00+08:00",
  "valid_from": null,
  "review_after": null,
  "supersedes": "mem_101:1"
}
```
这里有两个重要选择。

保留历史，但普通读取默认使用当前有效版本。

旧的 PostgreSQL 记录保留为历史，不再和 MySQL 平等地参与“当前数据库是什么”的检索。

区分信息来源的性质。

```text
user_statement   用户明确表达
tool_observation 工具实际观察
document_claim   文档中的陈述
inference        Agent 的推断
```

“用户说配置是 MySQL”和“实际配置文件显示 MySQL”不能被压成完全相同的证据。

### 功能一：提取与写入，采用“候选 → 校验 → 生效”
我会提供两个入口：

```python
propose_from_source(source_id)
remember_explicitly(content, scope, source_id)
```
前者用于自动提取，后者处理明确的“记住……”要求。两者都需要检查来源与范围。

流程：
```text
原始来源
  → LLM 提取原子候选
  → 校验结构、来源和范围
  → 查找已有相关记忆
  → 决定新增、补充、修订或冲突
  → 事务提交
```
LLM 输出类似：
```json
{
  "kind": "semantic",
  "subject": "orders_project",
  "predicate": "database",
  "content": "订单项目使用 MySQL",
  "suggested_scope": "project",
  "source_refs": ["source_245"],
  "operation_hint": "replace"
}
```

其中 suggested_scope 和 operation_hint 都只是建议，应用重新检查。

设置明确的写入策略：

| 内容 | 默认处理 |
|---|---|
| 用户明确表达的持续偏好 | 校验后生效 |
| 工具确认的项目事实 | 校验适用范围后生效 |
| 文档中的事实 | 保留文档来源与时间，按该领域的来源策略处理 |
| Agent 自己的推断 | 保持候选 |
| 一次执行经历 | 保存案例，明确结果和验证条件 |
| 从案例归纳的方法 | 保持候选，验证后生效 |

Mem0 当前的追加式写入给我的启发是：先保存新陈述，再明确决定它与旧记忆的关系，避免抽取时直接破坏历史。[Mem0 当前写入设计](https://docs.mem0.ai/core-concepts/memory-operations/add)

### 功能二：更新、冲突与时间管理

不会采用“最新写入的一定正确”，按三种情况处理。

1. 明确纠正：替代旧值。
    ``` text
        旧：默认用中文解释
        新：以后默认用英文解释
        
        → 创建新版本，旧版本标为 superseded。
    ```
2. 事实变化：保留变化关系。
    ```text
       旧：项目使用 PostgreSQL
       新：项目已迁移到 MySQL
       → 当前值更新为 MySQL，保留旧版本。
       → 只有来源给出迁移时间，才填写对应有效时间。
    ```
3. 来源矛盾：标记冲突或触发复核。
    ```text
       旧文档：使用 PostgreSQL
       当前配置：使用 MySQL

        → 根据该属性的来源策略处理。
        → 配置是直接依据时，可以更新当前值并标记文档过期。
    ```
来源策略按属性定义：
```python
policies = {
    "response_language": UserPreferencePolicy(),
    "database": ProjectConfigurationPolicy(),
    "deployment_status": RuntimeObservationPolicy(),
}
```

这样用户本人对语言偏好的表达可以直接成立，而运行状态需要工具确认。

数据库提交采用版本检查：

```python
with transaction():
    current = lock_current_memory(key)

    assert current.revision == expected_revision

    new_revision = insert_revision(candidate)
    supersede(current)
    set_current(new_revision)

    enqueue_index_refresh(new_revision)
```

这部分借鉴 Graphiti 的时间与失效思路，但先用关系表实现。更新时间、现实有效时间、需要复核的时间分别保存。[Graphiti 时序设计](https://www.getzep.com/blog/beyond-static-knowledge-graphs/)


### 功能三：读取采用三条路径
| 读取路径 | 用途 | 实现 |
|---|---|---|
| 常驻读取 | 少量高频偏好、关键项目约束 | 按明确的键读取 |
| 属性查询 | 当前数据库、某项决策 | 按范围、实体和属性查询 |
| 经验检索 | 类似故障、相关方法 | 全文与向量混合检索 |

例如开始一个编码任务：

```text
常驻读取：
语言偏好、当前项目关键约束

属性查询：
数据库、运行版本、构建方式

经验检索：
与当前故障相似的历史案例
```

整体检索流程：

```text
确定授权范围
  → 精确查询 / 全文召回 / 向量召回
  → 回主库核对版本、状态、权限、时间
  → 检查适用条件
  → 去重与重排
  → 按预算返回正文和来源
```

常驻部分借鉴 Letta 的分层方式，但我会限制大小。详细资料只在需要时读取，避免长期记忆越多，每轮输入越大。[Letta MemFS 的分层加载](https://docs.letta.com/concepts/memfs)

检索器返回：
```python
MemoryResult(
    content=...,
    scope=...,
    revision=...,
    evidence_refs=...,
    observed_at=...,
    applicability=...,
)
```
上下文构造器再决定如何呈现。记忆正文作为背景材料使用，不会因为被检索出来就获得修改应用规则或授权外部操作的权限。

#### 功能四：压缩与归并，生成派生记忆

长期记忆的压缩，实现三种操作。

重复归并。

同一范围、同一含义的事实归到同一记忆，增加证据关联。完全相同的文本可以用哈希筛选，语义相似内容再交给模型判断。

案例提炼。

从多次经历提取共同经验：

```text
多次原始执行记录
  → 相同问题与条件
  → 有证据支持的处理经验
```

不能因一次成功，就升级成普遍流程。

主题概览。

生成项目概览或决策索引，帮助快速定位明细：

```text
项目概览
├─ 当前技术栈 → 具体事实版本
├─ 关键决策   → 决策记录
└─ 已知问题   → 历史案例
```
所有派生记忆都记录依赖：

```text
summary_10:3
  depends_on:
    mem_101:2
    mem_203:1
```

底层事实变化时：

```text
标记派生记忆 stale
  → 暂停把它当作确定依据
  → 后台重新生成
```
这是优先补齐的能力。有总结功能，还需要有“原信息变化后，总结如何更新”的机制。

后台管理可以参考 LangMem 的抽取、更新和归并组件，但提交策略与依赖失效由应用控制。[LangMem 管理接口](https://langchain-ai.github.io/langmem/reference/memory/)

#### 功能五：失效、归档、撤回和删除

提供独立接口：

```python
revalidate(memory_id)
archive(memory_id)
retract(memory_id)
delete(memory_id, mode="hard")
```
| 操作 | 行为 |
|---|---|
| 复核 | 易变事实到期后重新查询来源 |
| 归档 | 保留历史，退出默认召回 |
| 撤回 | 立即停止使用，并处理派生影响 |
| 彻底删除 | 清理正文、版本、索引、缓存和相关派生内容 |

遗忘策略按类型设置：
- 用户明确的稳定偏好：不因长期未访问自动删除。
- 环境配置和运行状态：设置复核条件。
- 历史案例：可以转冷存储。
- 已被替代的事实：保留历史查询能力，退出当前事实召回。
- 无依据的候选：超过保留期后清理。
删除来源后，需要重新计算依赖：一个结论如果还有其他独立支持，可以重新验证后保留；只有被删来源支持的结论应停止生效。

对于“以后不要记住这个信息”，还要保存相应的写入策略，防止后台再次从历史中提取。


#### 功能六：索引一致性和并发控制
这部分直接影响系统是否可靠。

我会以 PostgreSQL 为主存储，向量与全文索引是可重建的读取结构。

每次更新在同一事务里写入：

```text
记忆版本变化
+ outbox 事件
```

后台消费：

```text
memory.updated
  → 生成新 embedding
  → 更新索引
  → 失效缓存
  → 标记依赖概览需要重建
```

任务携带：

```text
memory_id + revision + operation_id
```

工作进程执行前检查版本和撤回状态，防止旧任务覆盖新版本，或把已删除内容重新写回索引。

索引暂时落后时，检索结果必须回主库复核；刚发生的明确纠正，可以直接从主库按键读取，确保本轮使用新值。

#### 功能七：审计与效果评估

每条有效记忆，希望都能回答：

```text
为什么保存？
来源是什么？
适用于哪里？
被谁、在什么时候修改？
为什么被替代或撤回？
哪些总结依赖它？
```

同时记录检索使用情况，但把它与真实性分开：

```text
被召回次数：用于分析检索与成本。
证据支持程度：用于判断能否作为依据。
```

准备一组固定测试：

| 测试 | 验证内容 |
|---|---|
| 用户纠正偏好 | 下一轮不再使用旧值 |
| 项目事实变化 | 当前查询与历史查询各自正确 |
| 两个项目内容相似 | 不串用范围 |
| Agent 产生猜测 | 不自动变成已确认事实 |
| 删除来源 | 派生总结不会继续传播旧内容 |
| 索引更新延迟 | 不返回失效版本 |
| 多任务并发修改 | 不静默覆盖 |
| 类似任务重现 | 记忆是否改善最终执行结果 |


#### 实际落地顺序
分三阶段，避免一开始把整个系统做得过重。

| 阶段 | 实现功能 |
|---|---|
| **第一阶段：可靠记录** | 来源、原子记忆、范围、版本、显式纠错、精确读取、撤回 |
| **第二阶段：有效检索** | 全文与向量召回、适用条件、重排、上下文预算、索引同步 |
| **第三阶段：持续维护** | 经验提炼、方法验证、派生依赖、复核、归档与完整删除 |

第一阶段就可以支撑跨任务偏好和项目事实。第三阶段则让系统逐步积累可复用经验。

把纠错、来源追踪和版本失效放在自动总结之前完成：长期记忆持续增长后，最需要保证的是新信息能正确替代旧信息，而且每个结论仍然找得到依据。
