## 实现基于段落的语义分块

按照字符位置切分存在几个问题：

```text
1. 可能把一个段落从中间切开。
2. 可能把一句话或一个代码示例拆成两半。
3. 不能很好地保留文档原有的结构。
4. 即使设置了 overlap，也不一定能保证上下文完整。
```

优先按照空行拆分段落。

1. 尽可能把多个短段落合并到一个 Chunk。 
2. 超长段落再使用字符切分。 
3. 保留现有的 DocumentChunk 数据结构。 
4. 添加边界测试。 
5. 将新的分块器接入 PDF 构建流程。


### Chunking 不是简单的字符串截断
Chunking 是在几个目标之间做平衡：
```text
Chunk 太小
  ├── 上下文不足
  ├── 检索结果碎片化
  └── 需要召回更多 Chunk

Chunk 太大
  ├── 检索精度可能下降
  ├── 相关信息被无关内容稀释
  └── LLM 上下文成本增加
```
因此，chunk_size=500 和 overlap=50 不是通用的最佳参数，而是需要通过评估数据验证的实验参数。

### 文档结构比盲目 overlap 更重要
对于技术文档，以下信息通常具有较高价值：

* 标题和章节。 
* 完整的定义。 
* API 参数说明。 
* 配置示例。 
* 代码片段。 
* 前置条件和限制条件。

如果为了添加 overlap 而把段落从中间切开，可能反而损害文档结构。

### Chunk 的质量最终由检索评估决定

当前我们可以做结构性检查，但还不能断言 Chunking 已经适合问答。
后续需要通过 Golden Dataset 测试：
```text
用户问题
   │
   ▼
检索 Top-K
   │
   ▼
相关 Chunk 是否被召回？
   │
   ▼
Recall@K
```

如果相关 Chunk 总是没有被召回，那么即使 LLM 本身能力很强，最终回答也可能不正确。


## 实现跨页 Chunking

按照段落分块导致一个逻辑问题：

```text
PDF 的页面边界不一定是语义边界。一个完整的段落、代码说明或章节内容可能跨越多个页面。
```
因此我们把流程调整为：
```text
PDF 页面
   │
   ▼
提取所有页面文本，并保留页码
   │
   ▼
按页面顺序合并成段落单元
   │
   ▼
段落优先分块
   │
   ▼
为每个 Chunk 计算实际的起止页码
   │
   ▼
DocumentChunk
```


## 识别文档章节和标题
我们已经完成了：

```text
PDF 文本提取。
段落优先分块。
跨页 Chunk。
page_start 和 page_end 来源信息。
```
章节识别已经接入 `build_chunks`：标题不会写入正文，段落可跨页，同章节短段落可合并，跨章节不会合并。

早期每个 Chunk 曾经是：
```python
section_title="Unknown"
section_path=[]
```
这会影响后续检索和引用。如果我们只保存正文，而不保存章节上下文，就很难区分它们在文档中的位置。规则驱动的章节识别器流程：
```text
原始文本
   │
   ▼
识别可能的标题
   │
   ▼
维护当前章节路径
   │
   ▼
将章节元数据附加到段落
   │
   ▼
构建带章节信息的 Chunk
```
