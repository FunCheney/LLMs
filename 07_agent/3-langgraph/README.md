### langgraph 定义

langgraph 是一个面向长流程、强状态、可分支、可循环、可人工介入场景的底层编排框架和运行时。它用“图+状态”来组织和运行 LLM 工作流/Agent 流程。

* 图：把每一步做什么，下一步往哪走构建成一张可执行的有向图。节点负责执行动作，边负责决定流向。所以天然适合表达顺序执行、条件分支、循环回退、并行分发。
* 状态：不是把变量散落在一堆函数里，而是维护一份贯穿整张图的“当前工作流快照”，例如历史消息、检索结果、草稿内容、工具返回值、当前评分、是否需要人工审核。
  节点读取这份状态，执行后再返回要写回状态的更新。

它用来解决流程编排问题：当 AI 应用不再是一条直线，而是需要判断、重试、保存状态、人工审核时，怎么把流程写得可控、可维护、可恢复、可观测。


#### langgraph 中的四个核心概念

1. State：状态，这张图当前保存了哪些数据。在代码中对应：TypedDict / dict / Pydantic schema。
2. Nodes：节点，每一步真正干活的函数。在代码中对应：普通 Python 函数、异步函数、内部调用 LLM/工具的函数。
3. Edges：边，当前节点跑完下一步去哪里。在代码中对应：add_edge、条件边、START、END。
4. Graph：图，由状态、节点、边组成的完整工作流。在代码中对应：StateGraph(...) 构建器，compile() 后得到可执行应用。


这四个概念里，下面几处最容易误解：

* 节点不一定非得是大模型调用。 节点本质是函数，它可以调 LLM，也可以只是做加减法、查数据库、调用 API、做格式转换。 
* 边不一定只是固定顺序。 A → B 是最简单的普通边，后面第 24 章还会讲条件边、动态分发、Command 等更灵活的控制方式。 
* 状态更新通常是“节点返回局部字段更新”，不是每次手动拼完整状态。 比如节点只返回 {"greeting": "你好,z3"}，框架会按规则合并回全局 State。 
* 如果某个字段要“追加”而不是“覆盖”，就要考虑 Reducer

#### 能力

1. 持久化执行：长流程任务失败后，可以从检查点恢复，不需要从头在跑
2. 人机协作：需要加入人工审核，修改状态，确认好再继续
3. 记忆管理：对话历史，阶段性结论，跨轮上下文需要保存和复用
4. 流式处理：希望边执行边看到中间过程、Token 输出或自定义进度事件
5. 生产级部署与可观测：想把图变成可运维、可追踪、可调试的线上应用
